## Day 1 思考题

1. ReAct 里的"思考"步骤不会改变外部环境，为什么它还有用？
   - 我的回答：思考有多种作用，如把复杂任务拆成多个子目标分步执行、搜索之后总结材料、规划下一步、异常判断等，可以克服只推理（CoT-only）和只行动（Act-only）两种模式的局限。
   - 点评（✅ 基本到位）：回答了"思考能做什么"，还要补上"为什么有用"的机制——
     - 模型下一步动作只取决于上下文。思考不改变环境，但改变**模型自己的上下文**（工作记忆），后面的动作以写下来的中间结论为条件。论文写法：动作空间扩成 Â = A ∪ L，思考是语言空间里的动作，只更新上下文、不触发环境反馈。
     - 计算量角度：Transformer 每个 token 的计算量固定，写出推理过程 = 用更多 token 换更多串行计算。
     - 代价：思考花 token 和时延。"什么时候值得思考 / 搜索"本身就是算力分配问题，正是本项目"自适应"要解决的。
     - 类比：搜索系统里的 Query 理解模块，本身不返回商品，但决定后面走哪路召回、怎么改写。
2. 为什么检索回来的内容要从训练损失里遮掉？不遮会怎样？
   - 我的回答：检索内容属于观察，来自搜索引擎，不在模型能改变的范围内。如果不遮，搜索引擎返回的 token 很多，真正需要算损失的部分会被淹没，模型得不到有效更新。
   - 点评（⚠️ 方向对，主要理由要纠正）："淹没"只是次要因素，就算检索内容很短也照样要遮。问题出在梯度方向，不在大小：
     - **数学上没意义**：策略梯度 ∇J = E[Σ A_t · ∇log π(a_t|s_t)] 只对策略自己采样的动作求和；检索 token 是环境写进来的，对它们算 log π 再乘优势没有意义。PPO 的重要性比率同理。
     - **会学歪**：不遮 = 训练模型在 `<information>` 后面自己续写文档。优势为正时，模型学会编造检索结果（幻觉），甚至不调搜索直接脑补；优势为负时，又压低了真实文档的概率，引入噪声。
     - **易混点**：遮的只是梯度，前向计算时模型仍然能看到检索内容（`loss_mask` 不影响注意力）。
     - 你说的"淹没"体现在 `ray_trainer.py:864` 的 `state_tokens/coverage`（模型自己生成的 token 占比）上，但它是附带问题。
3. 奖励只看最终答案对不对，模型是怎么学会"该搜什么、什么时候搜"的？
   - 我的回答：模型在 PPO 过程中会学到哪些步骤或思考方式最终能得到正确答案，然后强化这种能答对的做法。
   - 点评（⚠️ 太笼统）：这说的是结果，没讲机制。核心问题是**信用分配**（credit assignment）：奖励只在最后给一次，怎样传到中间的搜索词上？
     - **探索是前提**：RL 只能强化采样里出现过的行为。基座模型从来不搜，给多少奖励也学不会。
     - **组内对比（GRPO）**：同一题采 5 条轨迹，A_i = (r_i − 组内均值) / 组内标准差。答对轨迹里所有模型生成的 token（搜索标签、搜索词、`<answer>`）都被提高概率，答错的被压低。同题几条轨迹往往就差在"搜没搜、搜了什么"，所以信号正好落在这些决策上。PPO 则靠价值模型加 GAE 把奖励往前分摊。
     - **统计累积**：单条轨迹很噪，但跨大量题目平均后，只有和答对稳定相关的决策会被强化。
     - 类比：广告里的**转化归因**；GRPO 组内归一化 ≈ 按同一请求分组做 listwise 比较，消除题目难度偏差。
     - 本项目切入点：`qa_em.py` 的奖励没有成本项，模型只学"怎样答对"，不学"怎样用最少的搜索答对"。
4. 对照 `infer.py`：谁负责让模型停下、谁去执行搜索、谁把结果拼回去？
   - 我的回答：`StopOnSequence` 负责停下，`search(query: str)` 执行搜索，`curr_search_template` 负责拼回去。
   - 点评（✅ 正确）。补充：
     - 停下有两种：`StopOnSequence`（L31-50，遇到 `</search>` 暂停去搜）和 EOS 判断（L109，答完退出）。比较的是 token id，所以 L83 要列 6 种 `</search>` 写法（带空格或换行时 BPE 分词结果不同）。
     - 解析是 `get_query`（L52-59），拼回是 L125-126 的 `prompt += search_text`。每轮都把整个 prompt 重新编码、从头计算，不复用 KV cache。
     - 隐患：① `while True` 没有轮数上限；② `get_query` 在包括 prompt 在内的整段文本上找最后一个 `<search>`，而 prompt 自带 `<search> query </search>` 示例，生成被截断时会拿旧查询或 "query" 去搜，静默出错；③ `requests.post` 没有超时和异常处理；④ 空查询也照搜。→ 分别对应 1.3～1.5 的 Budget、解析范围与异常返回格式、空结果测试。

### 1.3 思考题（写 `agent/parser.py` 之前要定下来）

1. 模型本轮没写 `<tool_call>`，直接输出一段话。当成最终答案，还是当成 `no_action` 错误？
   - 我的回答：不清楚。
   - 讲解：
     - 宽松（当答案）：EM 拿整句去比照样错，占不到便宜；更糟的是"I need to find…"这种话也会被当成"模型决定停下"，**污染停止决策的统计**。
     - 严格（当错误）：报错拼回给模型，下一轮改正；多花一轮生成但不花搜索次数（所以 `max_turns` 和 `max_search_calls` 要分开）。风险：模型格式差时，分数反映的是"不会写格式"而非"不会搜"。
     - 公平性：Search-R1 `qa_em.py` 的 `extract_solution` 要求 `<answer>` 至少 2 个才取最后一个，因为 prompt 里有示例 `<answer> Beijing </answer>`。和 `get_query` 同一个毛病，补丁很脆弱（prompt 删掉示例 → 所有正确答案被丢掉）。**所有方法必须共用同一套答案提取规则**，否则差距可能来自提取规则而不是策略。类比：A/B 实验两组埋点口径不一致。
     - 决定：严格；Direct / Static RAG 也通过 `final_answer` 作答（Direct = 搜索上限为 0 的 Agent）；轨迹保存原始输出，离线算宽松诊断指标，量化"因格式损失的分"；先严格，看数据再放宽。
2. 轮数用完了还没作答：直接判 0 分，还是再给一轮"只许答"的机会？
   - 我的回答：可能选第二种好一点，总体准确率略高，也会增加平均搜索次数。
   - 点评（✅ 选对了，"增加搜索次数"要细看）：
     - 强制轮禁止搜索，**实际执行**的检索次数不变；增加的是生成 token 和时延。
     - 但 Search-R1 的统计确实会多算：强制轮（`generation.py` L296-304，`do_search=False`）模型写了 `<search>` 仍记 `is_search=1`，计入 `valid_search_stats`，实际没执行。→ 要分开记"尝试次数"和"实际执行次数"，成本按实际执行算。**口径不同，数字就不同。**
     - 强制作答会掩盖"模型是自己知道该停，还是被预算截停"。按 `stop_reason ∈ {answered, forced_answer, no_answer}` 拆开报告；`forced_answer` 占比本身就是自适应停止要优化的指标。
     - 比 Search-R1 更明确的两处：① 强制轮占 `max_turns` 的最后一轮（Search-R1 是额外 +1 轮），保持硬上限；② 明确告诉模型"最后一轮、只能作答"（Search-R1 靠 RL 从奖励里学会这条规则；不训练就只能写进上下文）。

### 1.4 思考题（写最小循环之前要定下来）

1. Mock 检索工具为什么要做成确定性的？如果在 mock 里直接放进 gold 段落或答案，会有什么问题？
   - 我的回答：模拟真实检索引擎，对相同 query 返回相同内容。如果直接放 gold 段落，模型会误以为所有 query 都能返回标准答案，就学不到该怎么写 query 了。
   - 点评：
     - 前半句结论对、理由要换：真实检索不一定确定（索引更新、向量检索是近似的、同分文档顺序会变，所以 plan Day 2 要"固定相同 Query 的 TopK 顺序"）。真正原因是**可复现 + 控制变量**：测试失败能复现；方法间差距不能来自检索波动；轨迹能从 JSONL 重放。类比：离线评估固定样本和特征快照、A/B 实验只让策略不同。
     - 后半句在 **RL 训练场景（V3）完全正确**：环境总返回 gold，策略学到"随便搜都行"。但 V1 不训练，更直接的问题是：① 答案是喂进去的，准确率失真，测试因为错误的原因通过；② mock 要返回 gold 就得读标签，代码里留下泄漏通道。
     - 防泄漏靠接口签名：`search(query, top_k)` 拿不到题目 ID，物理上读不到标签。
     - 区分：语料**包含**答案是正常的；问题是工具**根据标签挑结果**。旧 `hotpotqa_corpus.jsonl` 是否只有 gold 段落，是同一问题的放大版（Day 2 核查）。
2. 怎样才算"重复"查询？被拦下的要不要扣搜索预算？
   - 我的回答：只差大小写/空格比较好；完全相同会有遗漏，语义判断成本高、不好判断。
   - 点评（✅ 选择和推理都对）：
     - 判定原则：检索器认为一样就算重复。BM25 分词会丢标点，所以标点也要归一化。类比：查缓存前的 query 归一化。
     - 语义去重最大的风险是**误判**：`Tessa Marrow` vs `Tessa Marrow birthplace` 语义接近，但后者是正当的追加限定词。误拦一次可能答错，漏放一次只多花一次搜索 → 宁可漏判，不可误判。
     - 补充：执行后看结果重合度（`num_new_docs`），只记录、不拦截。零成本抓到"换了说法的重复"，也是 V2 自适应停止的特征（边际收益）。类比：多路召回按 item id 去重。
     - 预算（没答的半题）：没执行 → 不扣搜索次数；这一轮生成花了 → 扣轮数；`search_attempts` +1。拦截本身几乎零成本，成本在模型白生成了一轮；`max_turns` 兜底防死循环。

### 1.5 思考题（写冒烟测试之前）

1. 用假模型（`ScriptedLLM`）做测试，能验证什么、不能验证什么？冒烟测试全过，能不能说"Agent 能用"？
   - 我的回答：能测试整体流程是否跑通，不能验证 LLM 相关的结论，如是否能理解检索结果并正确使用。冒烟测试通过后，还要确认检索结果是否正常、模型能否理解检索结果并输出正确答案。
   - 点评（✅ 核心判断对）：
     - 精确说法：它验证的是**控制逻辑**（预算记账、错误路由、停止原因、报错是否拼回），确定的逻辑用确定的输入测。
     - 另外两类盲区：① 剧本是我们编的，只覆盖**想得到**的错误（和黑名单同一个盲点），真模型怎么写错只有真跑才知道；② 接口没验证：`role="tool"` 在 Qwen 模板里的实际渲染、真实检索的时延和失败方式。
     - 还缺的证据（Day 3）：小 validation 集上的格式有效率、错误类型分布、人工抽查轨迹（虚构语料 → 答对只能是用了检索结果）。
     - 类比：排序服务的单元测试证明管道没写错，效果要靠离线评估和 A/B。
2. 要不要在每轮观察里告诉模型"还剩几次搜索"？
   - 我的回答：不太清楚，直观感觉没必要。告诉之后 forced_answer 可能更少，比较可能不太公平。
   - 点评（⚠️ 结论对，理由要换）：
     - 区分**公平**和**干扰测量**。公平 = 资源和评分口径相同；Static RAG 没有决策，告诉它预算没意义，所以不存在不公平。真正的问题是干扰测量：forced_answer 变少，可能是模型会数数了，而不是会判断"信息够了"，弄脏核心指标。
     - 副作用：① 锚定效应，把预算当目标、简单题也搜满（年底突击花预算）；② 提示词随预算变化，`Budget ∈ {1,2,3,5}` 曲线分不清是资源多了还是提示词不同。
     - 但它确实是一种策略：类比广告**预算平滑（budget pacing）**，出价器知道剩余预算来调节奏。→ 作为 V2 的**零成本对照基线**：花大力气做的路由/停止策略连它都比不过，就不值得做。
     - 决定：V1 不告诉；V2 作为消融项，届时再加开关。

### 1.6 思考题

1. 为什么每次实验要保存 `git_commit.txt`？工作区有未提交改动时怎么办？
   - 我的回答：便于回溯 debug；有未提交改动就不能代表实际代码，所以要先提交。
   - 点评（✅）：补两点。① "先提交"靠人记不住 → runner 自动检查，有改动就拒绝运行，调试可 `--allow-dirty`，但会存 `git_diff.patch`、目录带 `-dirty`。② 结果由**代码 + 配置 + 数据 + 环境**四样决定，commit 只锁住代码，其余记在 `config.yaml`（数据清单 Day 2 做）。
2. 模型调用出错怎么记？
   - 我的回答：先重试，设最大重试次数，超过之后就跳过。
   - 点评（⚠️ 重试对，"跳过"有问题）：跳过 = 从分母里去掉，而失败的往往是难题 → 准确率虚高；Agent 多轮更容易超时，方法间就在不同题集上比较。类比：推荐离线评估丢掉超时请求（常是冷启动/长尾用户），属于样本选择偏差。
   - 做法：只重试临时性错误（超时、断连），指数退避，最多 3 次；仍失败记 `stop_reason=error`、计 0 分、留在分母里；同时报"去掉失败题"的诊断指标和失败率；失败率 > 2% 判本次运行无效。

   - 点评（⚠️ 拆分的方向对，① 的原则对；但实测这次两个子查询都变差了，② 的机制也不对）：

       | Mary Gordon birth year（模型的改写） | 2（第 1 是圣母诞生） | — |

       | Mary Gordon writer | **1** | — |
       | H. L. Mencken journalist | — | **2** |

     - ① 说法：库里怎么写其实可以预知。维基人物段落第一句只有两种写法：在世的写 `(born December 8, 1949)`，已故的写 `(September 12, 1880 – January 29, 1956)`，连 born 都没有。`birth` 两种都对不上，还把 "Nativity of Mary" 招了进来。
     - ② 机制：两人没有共同段落，问题不在"交集"。真正的原因是各词相加导致抢名额：Mary Gordon 的段落能命中 mari、gordon、writer、born 四个词，总分压过只命中 mencken 的段落，把 Mencken 挤到第 5。
     - ③ 拆开不会自动变好：单独搜 Mencken，他妻子（Marion Bloom）、父亲、故居的段落里 mencken 出现 4～5 次，他本人简介只有 2 次，金标掉到第 8。原问题里的 `writer` 反而帮了忙（简介里有 "writers"）。HotpotQA 的干扰段落本来就是拿问题做 TF-IDF 检索挑出来的，专门难为词匹配检索器，类似困难负样本。
   - 启示：拆分是对的策略（前 3 名放不下两个实体），但每个子查询要写成"文档里会怎么写"（实体名 + 类型词，如 `H. L. Mencken journalist`），而不是"我想问什么"（`birth year`）。查询好坏靠直觉判断不了，要用证据召回来量，这也是 V2 加向量检索、V3 用 RL 优化查询的动机。类比：工业 Query Rewrite 要把用户的说法改写成商品/广告那一侧的说法。

### 3.3 思考题（真模型第一次跑完 debug 集后）

1. 证据全部找齐的 21 题里仍答错 10 题。这对"算力该加在哪"有什么启示？面试官问"答错主要是检索的问题还是模型的问题"，怎么用数据回答？
   - 我的回答：说明 3B 模型能力不足，可能要换更大的模型。可以对不同尺寸的模型做消融，换大模型后问题解决了，就说明是模型的问题。
   - 点评（⚠️ 消融的思路对，但结论下早了，实验设计有混杂）：
     - **先拆错因，再下结论**。逐条看这 10 题：约 5 题意思答对了、被 EM 判错（December vs December 1969、Latvia vs Latvian、答了一句话而不是 yes）；1 题标签本身有问题（问"有什么不同"，金标是 "yes"）；真正读错的约 4 题（比较距离比错、停在第一跳答了电影名而不是演员、yes/no 题答 "unsure"）。→ 真正的"读错"只占 50 题里的 4 题左右。
     - **看全局比例**：50 题里答错 36 题，其中 **26 题证据没找齐**，证据齐了还错的只有 10 题。按错题数算，检索仍然是更大的瓶颈。类比：排序模型效果差，先看是召回没召回到，还是排序排错了，再决定加在哪一层。
     - **消融有混杂**：换大模型后，查询写得更好、停得更准、格式更稳，都会一起变，准确率涨了也说不清是"读得更好"还是"搜得更好"。要单独测"读"的能力，得把证据固定住：直接把金标段落给模型（oracle context，理想证据上限），这时答错只能怪读。三个数一拆就清楚：B0（无证据）→ Agent（自己搜）→ Oracle（完美证据），Agent 到 Oracle 的差距是检索损失，Oracle 到 100% 的差距是阅读损失（含标签噪声）。模型尺寸消融放在 Oracle 设定下，测的才是纯阅读能力。
   - 启示：
     - 算力分配不只有"多搜几次"一个旋钮，还有"用多大的模型读"。错因在检索时，加搜索有用；错因在阅读时，加搜索没用，要加在阅读端。"简单题用小模型、难题换大模型"本身就是一种自适应算力分配（模型路由），可以作为 V2 的候选方向。
     - 下结论前先确认量尺准不准：一半的"错"是评测口径造成的。→ 3.4 补 Token-F1。
   - 面试答法："我把错题按证据是否找齐拆开：36 道错题里 26 道证据没找齐，是检索问题；证据齐了还错的 10 道，逐条看一半是 EM 太严，真正读错的只有 4 道左右。所以当前瓶颈主要在检索。要单独衡量阅读能力，我用金标段落做理想证据上限，再在这个设定下比较不同尺寸的模型，避免把'搜得更好'算成'读得更好'。"

### 3.4 思考题（基线跑完后）

1. 比较题上 Agent 不如 Static RAG。V2 的第一个自适应策略，根据什么信号决定"搜一次就答"还是"进入多轮"？信号在答题前拿得到吗？
   - 我的回答：不清楚（请 Claude 讲解）。
   - 讲解：这是**路由问题**，同搜索系统"先做 query 理解，再决定走哪条召回链路"。按拿到信号的时机分三层，越早越便宜、信息越少：
     | 时机 | 信号 | 代价 | 类比 |
     |---|---|---|---|
     | ① 检索前，只看问题 | 题型（比较 / 桥接）、问题里点了几个实体的名字 | 几乎为零 | query 意图分类选召回链路 |
     | ② 原问题搜一次之后 | 结果是否覆盖问题里的每个实体、检索分数 | 一次检索 | 召回质量不够时触发补充召回 |
     | ③ 模型读完证据之后 | 模型有没有把握、是否说"信息不够" | 一次生成 | 精排置信度低时走兜底 |
     - ① 拿得到：validation 上一条三行规则（含 "or" 或以 Are/Is/Was/Does 开头）认出比较题，精确率 95%、召回率 85%。盲区是实体没被点名："Does Darren Bravo's **half brother** bat left-handed or right-handed?" 像比较题，但"兄弟是谁"要先搜 → 需要 ② 补位。
     - **防泄漏陷阱**：数据里的 `type` 字段在答案文件里，推理时不能读，必须从问题文本预测。面试官很可能追问。
     - 由此得到 V2 候选策略：**级联（cascade）**。第一次检索永远用原问题（成本 = Static RAG）；比较题且结果覆盖两个实体就直接作答；否则再进多轮 Agent。类比推荐的粗排 → 精排：便宜的一层处理大部分请求，难的才交给贵的一层。
   - 面试答法："我用答题前就能拿到的信号做路由：问题文本判断题型，第一次检索的结果判断证据够不够。比较题的两个实体都在问题里，搜一次就够；桥接题的第二跳实体要读了第一跳才知道，才值得多轮。题型标签在答案文件里，不能直接用，要从问题文本预测。"

## 概念卡片

### 工具调用 = 约定的文字格式 + 外部控制循环

模型只会输出文字。`infer.py` 里模型写到 `</search>` 时，由停止条件打断生成，外部程序解析出搜索词、调用检索、把结果用 `<information>` 包好拼回输入，再让模型继续写。

### 思考 = 只改上下文、不改环境的动作

ReAct 把动作空间扩成 Â = A ∪ L。思考不触发环境反馈，但把中间结论写进上下文，后续动作以它为条件；同时用更多 token 换更多串行计算。代价是 token 和时延。

### 检索内容遮罩：遮梯度，不遮注意力

策略梯度只对策略自己采样的动作有定义。检索 token 是环境写进来的，参与前向计算，但不进损失。不遮会让模型学会自己编文档。

### 结果奖励 + 组内对比 = 信用分配

只在最后给一次奖励（EM）。GRPO 在同一题的多条轨迹间做归一化，答对轨迹的每个生成 token（包括搜索决策）一起被强化。前提是模型能探索到正确行为；缺点是奖励没有搜索成本项。

### 动作校验分四层，每层各自报错

| 层 | 检查什么 | 错误码 |
|---|---|---|
| 语法层 | 能否从文字里解析出一个动作 | `no_action` / `invalid_json` |
| 结构层 | 工具名和参数是否合法 | `unknown_tool` / `invalid_args` |
| 策略层 | 合法但不该执行 | `duplicate_query` / `budget_exceeded` |
| 执行层 | 工具本身出错 | `tool_error` |

"检索成功但没结果"不是错误（`ok=True, docs=[]`）。类比：召回为空和召回服务超时是两种不同的告警。

### 动作格式：标签负责定位和停止，JSON 负责内容

采用 Qwen2.5 原生的 `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`。训练、评测、推理共用同一个解析器，避免 train-serve skew（线上线下不一致）。

### `agent/schema.py` 的三个设计决定

1. 数据结构（schema）和文字格式（parser）分开放，换格式只改解析器。
2. "停止作答"也是一个动作（`final_answer`）：每轮恰好一个动作，"何时停"被显式记录，才能统计和优化（Cost-aware Stop）。
3. `top_k` 由配置固定，不交给模型：保证和 Static RAG 拿到同样多的证据，比较才公平。
4. 补充：`Budget`（上限，放进 config.yaml，创建后不可改）和 `BudgetState`（用量，写进轨迹）分开；`max_turns` 连写错格式的轮次也算，是防死循环的硬上限，`max_search_calls` 才是实验里要权衡的成本。

### 解析严格 + 口径统一

- 纯文字不当答案（严格）；所有方法共用同一个解析器和答案提取规则。宽松指标只作为离线诊断。
- 解析器只管语法层和结构层；策略层在循环里，执行层在检索网关里。
- 一轮写多个 tool_call：只执行第一个（与 Search-R1 训练代码一致），个数 `num_tool_calls` 记进轨迹。

### 停止原因要拆开记

`stop_reason ∈ {answered, forced_answer, no_answer}`。强制作答提高准确率，但会掩盖模型会不会自己停；`forced_answer` 占比是自适应停止的核心指标。搜索次数分"尝试"和"实际执行"，成本按实际执行算。

### 1.4 最小循环的几个设计点

- **防泄漏靠接口**：检索工具只收 `query, top_k`；`qid` 只进轨迹用于对齐。
- **Mock 语料用虚构实体**：接真模型后它没法凭记忆作答，答对就说明确实用了检索。
- **模型接口只有"给消息、返回文字"**：测试用 `ScriptedLLM`（按剧本输出，完全确定），Day 3 换真模型不改循环。
- **强制作答的时机**：只在"最后一轮"或"模型在搜索次数用完后仍想搜"之后；搜索次数刚用完时不提前强制。这样 `forced_answer` 统计的才是"还想搜但被截停"。
- **三个计数**：`turns_used`（每轮都算）、`search_attempts`（想搜就算）、`search_calls_used`（实际执行才算，含超时）。成本按最后一个算。
- **检索出错**：算一次实际执行（请求已发出），但不记入"已搜过"，允许原样重试。

### 测试要能失败才有意义（改坏检查）

测试第一次就全绿，不能说明它有效。故意把关键设计改坏（本项目：解析范围、查询归一化），看对应测试能否抓到。1.5 里就靠这个发现：`test_prompt_example_is_never_executed` 原先设 `max_turns=1`，唯一一轮是强制作答轮，误解析出的搜索会被预算拦下、根本不执行，测试只是碰巧靠错误码抓到 → 改成默认预算。
这个做法叫 mutation testing（变异测试）；类比：检验监控告警，要故意注入故障看它响不响。

### 冒烟测试的分工

- `test_action_schema.py`：语法层和结构层（纯文字、截断、非法 JSON、未知工具、空查询、多写参数）+ Budget 校验和不可修改。
- `test_mock_search.py`：检索确定性（同查询同结果、同分按 doc_id、零命中返回空）。
- `test_loop.py`：策略层和执行层（重复查询、超预算、强制作答时机、轮数用完、空结果、检索出错）+ `infer.py` 回归测试 + 防泄漏 + 轨迹可以序列化后原样读回。
- 运行：`pytest tests/`，或 plan 验收命令 `python -m tests.test_action_schema`。

### BM25：词匹配打分（Day 2）

- 分数 ≈ 查询词在段落里出现得多（词频，有饱和上限 k1）× 这个词在全库里稀有（IDF）÷ 段落长度（长段落会被惩罚，参数 b）。
- 擅长人名、地名、专有名词的精确匹配；不懂同义改写（"创始人"和"创立者"对不上）。这正是 V2 要加向量检索、做混合检索的原因。
- 类比：搜索里的倒排召回（关键词召回），向量检索对应语义召回，两者合起来就是多路召回。

**公式**（bm25s 默认的 Lucene 版本，也是 Elasticsearch 的默认打分）：

```
score(q, d) = Σ_{查询里的每个词 t} IDF(t) × tf·(k1+1) / (tf + k1·(1 − b + b·|d|/avgdl))
IDF(t)      = ln(1 + (N − df + 0.5) / (df + 0.5))
```

`tf` = 词在这段里出现几次，`df` = 全库有几段包含这个词，`N` = 总段数，`|d|/avgdl` = 这段长度 ÷ 平均长度。

**三个因子，用我们语料池（N = 507,494）的真实数字说明**（2026-09-28）：

| 因子 | 在管什么 | 例子 / 效果 |
|---|---|---|
| IDF（逆文档频率） | 词越稀有越值钱 | `maigret` 只在 16 段出现，IDF=10.3；`who` 在 7.6 万段出现，IDF=1.9。命中一次 maigret 顶 5 次 who |
| 词频饱和（k1=1.5） | 出现次数多加分，但有上限 | 词频因子 tf=1 → 1.0，tf=2 → 1.43，tf=5 → 1.92，上限 2.5。防止靠堆砌关键词刷分，类似广告的频控 |
| 长度归一（b=0.75） | 长段落天然包含更多词，要打折 | b=0 不惩罚，b=1 完全按长度折算 |

**查询前的处理**：分词 → 去停用词（the、of 这类几乎每段都有的词）→ 词干化（`plays` → `play`，`Mary` → `mari`）。查询和建索引必须用同一套处理，否则词对不上。

**完整拆一道题**（2026-09-28 在语料池上实测）："Which writer was born earliest, Mary Gordon or H. L. Mencken?"

| 处理后的词 | which | writer | born | earliest | mari | gordon | mencken |
|---|---|---|---|---|---|---|---|
| 出现在几段里 | 90,311 | 14,642 | 84,016 | 1,787 | 6,460 | 1,896 | 24 |
| IDF | 1.73 | 3.55 | 1.80 | 5.65 | 4.36 | 5.59 | 9.94 |

- `was`、`or` 被当停用词去掉，`H.` `L.` 单字母被丢掉；`which` 不在停用词表里，但 IDF 很低，影响不大。
- 分数几乎由人名决定：命中一次 `mencken` 约等于命中 5.5 次 `born`。
- 结果：`Mary Gordon (writer)` 排第 1，`H. L. Mencken` 排第 5。我们 `top_k=3`，所以第二个金标会漏掉。**两个实体挤在一个查询里，会互相抢前几名的位置。**

**典型失败（词汇不匹配）**：搜 "Mary Gordon birth year"，排第 1 的是 "Nativity of Mary"（圣母诞生，Mary 和 Birth 各出现多次），正确段落 "Mary Gordon (writer)" 排第 2。它写的是 `born December 8, 1949`，而 `born` 和 `birth` 词干化后仍是两个词，BM25 认为它们毫无关系。向量检索和查询改写要解决的就是这类问题。

**词干化的两种失误**（2026-09-28 实测）：它只按词形砍后缀，不懂词义。
- 该合的没合：`founded` → `found`，`founder` → `founder`，是两个词。
- 不该合的合了：`founded`（创立）和 `found`（find 的过去式）都变成 `found`。搜 "Who founded Apple"，排第 1 的是小说 "The Apple Dumpling Gang"，因为它写着 "the gold the children have found"，而且段落短（51 词），长度折扣小。披头士的 "Apple Corps" 里 apple 出现了 13 次，但词频已经饱和，段落又长（139 词），只排第 2。Steve Wozniak 排第 3。
- 换成 "Apple founder" 搜，前 5 名换了一大半（History of Apple Inc. 第 1，Steve Jobs 第 3）。**同一个意图换一种写法，排序就变了**，所以 Agent 怎么写查询直接决定能搜到什么。

**为什么这么快（50 万段，约 10ms）**：倒排索引 = 词 → 包含它的段落列表，查询只看包含查询词的段落，不用扫全库。bm25s 还在建索引时就把每个（词, 段落）对的分数算好，存成稀疏矩阵，查询时只要把几行加起来。

**为什么 V1 先用 BM25**：HotpotQA 以实体为中心，人名、片名的精确匹配正好是 BM25 的强项；不用训练、CPU 就能跑、结果确定、分数可解释，适合做固定检索器，先把 Agent 本身的问题研究清楚。

### 证据召回：把"搜得好不好"和"答得好不好"分开（Day 2）

- `evidence_recall`：整条轨迹检索到的段落，覆盖了几个金标段落。`all_evidence_found`：金标全部找齐的比例。
- 答错可能有两种原因：没搜到证据（检索问题），或搜到了但没读懂（模型问题）。只看准确率分不开。类比：推荐系统里分别看召回率和排序 AUC，才知道瓶颈在召回还是排序。

### 检索体检的发现：为什么需要多轮、为什么需要自适应（Day 2）

- 原问题搜一次，前 3 条找齐两个金标：28%。桥接题前 20 条也只有 50%：第二跳实体（如 "David Connell"）不在问题里，只有读了第一跳（"Sesame Street"）才知道。
- 比较题两个实体都在问题里，一次搜索前 20 条能找齐 85%。
- → 多轮搜索有必要；不同类型的题需要的搜索量不同，这就是自适应分配搜索算力的依据。

### 语料池 vs 全量维基（Day 2）

- 语料池 50.7 万段（HotpotQA 所有题目自带的段落），全量维基约 520 万段。池子小一个量级，检索更容易，**实验表必须标注 `retrieval_setting=pool`**，不能说成开放域全库检索。
- 池子由整个数据集决定、不依赖抽到哪些题，所有方法用同一个池子，比较仍然公平。
- 后期扩容后用全量维基做鲁棒性验证：结论在更难的检索设定下是否仍然成立。

### 不训练的模型：提示词要顺着它微调时见过的格式（Day 3）

- 占位提示词（自己写的列表式工具说明）：Qwen2.5-3B 格式有效率 0/8，写成 `Search: Search({...})`；换成它微调时见过的原生工具说明（`# Tools` + `<tools>` 函数签名）：8/8。查询意图两种写法下都合理，差的只是"格式"。
- 原因：Instruct 模型的工具调用能力是用固定模板微调出来的，偏离模板就退化成模仿提示词的字面样子。不训练（V1/V2）时只能迁就模型；V3 做 RL 时才能反过来塑造格式。
- 停止词：原生模板允许并行调用，模型会一口气写"搜 A、搜 B、作答"，作答时根本还没看到结果。在 `</tool_call>` 截断，一轮只能一个动作，规则由代码强制。
- 类比：线上模型的特征格式要和训练时一致（train-serve skew）；提示词格式就是 LLM 的"特征格式"。

### 基线和 Oracle：把"答错"拆成检索损失和阅读损失（Day 3.4）

- **四种方法只差一个变量**：Direct / Static RAG / Oracle 用一字不差的提示词，只差用户消息里给了什么证据（无 / 原问题检索 top 3 / 金标段落）；Agent 用带 search 工具的提示词，证据自己搜。所有方法共用循环、解析器、预算和评测器。
- **三段差距各代表什么**：Direct → Static RAG 是"搜一次"的收益；Agent → Oracle 是检索还差多少（检索损失）；Oracle → 100% 是阅读损失（加上 EM 口径和标签噪声）。类比推荐：Oracle 相当于"召回里一定有正样本"时的排序上限，用来判断该优化召回还是排序。
- **debug 集上的发现**（50 题，只用于调试）：
  - 桥接题：Agent 0.22、Oracle 0.53 → 瓶颈在检索（第二跳实体要读了第一跳才知道）。
  - 比较题：Static RAG 0.50 已经等于 Oracle，Agent 反而 0.43 → 检索已经够了，瓶颈在阅读和答案规范；多搜不但浪费，改写还可能把检索搞坏。
  - Agent 输入 token 是 Static RAG 的 4 倍，P50 延迟 6 倍，整体只多 4 个点，逐题比 7 胜 5 负。
  - → **同样多花算力，桥接题有收益，比较题没有**，这就是按题型自适应分配搜索算力的依据，也修正了 3.3 思考题里"瓶颈主要在检索"的说法：要按题型说。
- **validation 200 题上的正式结果**（修正 debug 上的印象）：EM Direct 0.12 → Static RAG 0.32 → Agent 0.35 → Oracle 0.54。
  - 搜一次 +20 个点，最划算；Agent 再 +3 个点，逐题配对 bootstrap 95% 区间 [−3.5, +9.5]，**不显著**。debug 上"比较题 Agent 更差"方向还在，但 41 题的区间有 ±17 个点，说明不了。**小样本上的差距要报置信区间**，类比 A/B 实验看显著性而不是只看均值。
  - 阅读损失（Oracle → 100%，46 个点）比检索损失（Agent → Oracle，19 个点）还大。Oracle 答错的 92 题里 52 题 F1 > 0，多是答案形式问题。→ 3.3 思考题里用户说的"模型能力不足"在 validation 上更有道理了：先修答案格式，再在 Oracle 设定下做模型尺寸消融，是值得做的实验。
  - Agent 第一个查询比原问题更差（变差 26 题、变好 8 题），多轮后覆盖从 0.56 升到 0.68 → 多轮的收益来自多搜，不是改写写得好。和 BM25 那一节的结论一致：查询要写成文档会怎么写。
- **Oracle 为什么是诊断、不是方法**：它读了标签，违反"标签只给评测器"。只在 validation / debug 上跑、表里单独标注、代码拒绝 test。面试时要主动说明这一点。
- **Oracle 下比较题还错的原因**：多数是答案形式（问"谁"答成年份、答 "true" 不答 "yes"、照抄标题 "Firehose (band)"），真正推理错约 2～3 题。→ 答案规范可以靠提示词修，但只能在 validation 上调。

### vLLM：把模型变成一个高吞吐的在线服务（Day 3）

- **是什么**：大模型推理引擎 + 服务框架。加载一次模型，对外提供 OpenAI 兼容的 HTTP 接口（`/v1/chat/completions`），任何语言、任何进程都能调。本项目里它和检索服务一样，是独立进程（`verl_env`，8000 端口），Agent 代码只管发请求。
- **要解决的问题**：生成是一个 token 一个 token 往外吐的，每一步都要读前面所有 token 的 K、V 向量（KV cache，注意力的中间结果缓存，避免重复计算）。朴素实现有两个浪费：① 按最大长度给每个请求预留显存，大部分用不上；② 一批请求要等最长的那个写完才能换下一批。
- **两个核心技术**：
  - **PagedAttention**（分页注意力）：像操作系统的虚拟内存分页，KV cache 按 16 个 token 一块按需分配，不再整段预留。我们的服务：权重 5.8GB，其余显存分成 22,492 块 ≈ 36 万 token 的 KV cache，够 44 个 8K 长度的请求同时跑。
  - **Continuous batching**（连续批处理）：每生成一个 token 就重新组批，写完的请求立刻离开、新请求立刻加入，不用等整批结束。类比：推荐系统在线服务的动态 batching。
- **为什么 KV cache 装得下这么多**：Qwen2.5-3B 用 GQA（分组查询注意力），16 个查询头只配 2 组 K/V，每个 token 的 KV 只有 36 层 × 2 × 2 头 × 128 维 × 2 字节 ≈ 36KB，是标准多头注意力的 1/8。
- **我们用到的功能**：服务端套对话模板；`usage` 返回输入输出 token 数；`stop` 停止词（在 `</tool_call>` 截断）；`seed` 固定采样。
- **延迟由输出长度决定**（3.3 实测 53 轮回归）：延迟 ≈ 11ms + 0.044ms × 输入 token + 8.7ms × 输出 token。输入 token 占总量 92%，却只贡献 6% 的延迟；输出 token 占 8%，贡献 92%。原因：读输入（prefill，预填充）是一次并行算完的，写输出（decode，解码）是一个一个串行吐的。
  - 对项目的意义：**延迟看输出长度，算力和显存看输入长度**。多轮 Agent 每轮都把整段上下文重新读一遍，输入 token 随轮数累加（第 1 轮约 300，第 5 轮约 2000），这是它比 Static RAG 贵的主要来源；单请求延迟上不明显，并发高了就体现为吞吐下降。成本指标要把输入、输出 token 分开报。
  - 我们没开 prefix caching（前缀缓存，相同开头的请求复用 KV cache），开了之后多轮的输入成本会大幅下降，是 V2 可以讨论的系统优化。
- **在 RL 里的角色**：Search-R1 / verl 训练时用 vLLM 做 rollout（采样轨迹），训练时间大头是生成而不是反向传播，所以推理引擎的吞吐直接决定 RL 训练快慢。

### Search-R1 源码里的几个关键点

- 检索内容遮罩：`search_r1/llm_agent/generation.py` 的 `info_mask` → `verl/trainer/ppo/ray_trainer.py:859` 的 `loss_mask`。
- 奖励：`verl/utils/reward_score/qa_em.py` 只看最终答案是否与标准答案完全一致（EM）；`format_score` 默认 0，没有成本项。
- 答案提取：`extract_solution` 在整段文本上找 `<answer>`，少于 2 个返回 None（为了跳过 prompt 里的示例），很脆弱。
- 强制作答轮：`max_turns` 之后再加一轮 `do_search=False`；这一轮的 `<search>` 仍计入 `valid_search_stats`。
- 训练配置：`train_grpo.sh` 默认 8 卡、每批 512 条、每题采样 5 条轨迹为一组（`n_agent=5`）、最多搜 2 轮（`max_turns=2`）。

### 向量检索（Dense）：查询和段落编码到同一个向量空间（Day 8）

- **双塔结构**：查询和段落分别过编码器（e5-base-v2，BERT 结构，768 维）。段落向量离线算好存进索引，线上只编码查询，再找内积最大的段落。和推荐里的双塔召回（用户塔 / 物品塔，物品向量离线算好）是同一个结构。
- **e5 的用法**：查询加 `query: `、段落加 `passage: ` 前缀（训练时就这么加的，不加效果明显下降）；所有 token 向量取平均（mean pooling）；L2 归一化后，内积就是余弦相似度。
- **为什么不能直接拿 BERT 的向量**：没做过对比学习的句向量，意思相近的句子不一定靠得近。e5 用大规模（问题, 段落）对做了对比学习：拉近配对的、推远不配对的。
- **精确 vs 近似检索**：Flat 每次和全部向量算内积，50 万 × 768 维每次要读 1.5GB 内存，约 27ms，结果精确。HNSW（图索引，沿近邻图走）和 IVF（先聚类，只搜最近的几个簇）能快一两个数量级，代价是会漏召回。规模小用 Flat，比较更干净；全量维基（520 万段）才需要近似索引。
- **成本结构**：离线建索引一次（GPU 4 分钟）；线上每次查询 = 编码（模型前向，CPU 约 20ms）+ 检索（约 27ms）。比 BM25 贵几倍，但和一次模型调用（约 500ms）比仍然很小。

### BM25 匹配"提到"，Dense 匹配"关于"（Day 8 发现）

validation 200 题，原问题搜一次：Dense 召回@3 0.710，BM25 0.565；比较题 0.976 vs 0.585。抽查只有一路找到的金标：

- **只有 Dense 找到（79 段）**：① 问题用描述代替名字（"1996 年电影里演丹麦王后的" → Hamlet (1996 film)）；② 要找"讲的就是这个实体"的段落。比较题点名两个实体，Mick Jagger 被很多段落提到，BM25 按词频把"提到他"的段落排前面，Dense 把"关于他"的介绍段排前面。
- **只有 BM25 找到（20 段，全是桥接题）**：问题里有个罕见词（游戏名、人名）只出现在段落正文里，段落讲的是另一个实体（"Shipwrecker" → Mayfair Games 的介绍里提了一句）。Dense 把整段压成一个向量，只提一次的罕见词被稀释了。
- **一个反直觉的结果**：Dense 只搜一次（0.710）就超过了 V1 里 BM25 Agent 搜多轮（0.677）。换检索器的收益比多轮的收益还大。
- **要打的折扣**：e5 预训练数据里有维基的（标题, 段落）对，和 HotpotQA 段落的形式几乎一样，这里 Dense 的优势可能偏大。商品搜索里型号词、品牌词多，正是 BM25 擅长的，要重新验证。

### RRF：多路召回怎么融合（Day 8）

```
RRF(d) = Σ_{每一路 r} 1 / (k + rank_r(d))      某一路没召回 d，就在那一路记 0
```

- **为什么按名次不按分数**：BM25 分数没有上界（几到几十），余弦相似度挤在 0.7～0.9，量纲不同，直接相加等于让 BM25 说了算。要按分数加权得先做校准，RRF 只看名次，不需要校准。
- **k 的作用**：k=60（Cormack 2009）。k 越大，第 1 名和第 5 名的差距越小，越看重"几路都召回了"。
- **Day 8 结果：等权 RRF 没有超过 Dense**，比较题上还显著更差（召回@3 −12 个点）。融合要有用，前提是两路水平相近、而且互补。一路明显弱时，等权融合会把弱的那一路的错误结果拉进前排。Hybrid 只在前 10～20 条略高，说明它把候选收得更全，但顺序没排好。
- **类比**：多路召回里有一路质量很差，按配额等量混进来会拉低整体。解法要么给它降权，要么让下游精排来挑。后者就是 Day 9 Reranker 的位置：融合负责把候选收全，重排负责把顺序排对。

### 路由上限：先量"最好能多拿多少"，再决定要不要做路由（Day 8.7）

做法：每道题（或每一跳查询）事后挑召回最高的检索器，得到一个理想路由的上限。真实路由器只能逼近它，一般拿到一半就不错。上限本身就小时，这条线就不值得做主线。

| 金标召回@3 | HotpotQA | 2Wiki |
|---|---|---|
| 最强固定一路 | Dense 0.710 | Hybrid 0.602 |
| 逐题理想路由 | 0.765（+5.5） | 0.637（+3.4） |
| 两路打平的题 | 57% | 70% |

两个结论：
- **最强的一路依数据集而变**：HotpotQA 上 Dense 最强，2Wiki 上 Hybrid 显著更强。所以强基线必须按数据集用数据挑。这和推荐里"召回配比要按场景调"是一回事。
- **查询构造的影响远大于选哪一路**：2Wiki 上用整句问题去搜，Dense 召回 0.588；用标签里的三元组造出"实体 + 关系"这种干净的子查询，Dense 召回 0.968，三路全落空的只有 2%。同一个检索器、同一个语料，只换查询就差 38 个点，而换检索器只差 3～5 个点。

**类比**：在搜索里，查询理解（改写、纠错、拆解）的收益通常大于召回通道的调优。召回通道之间的差异是"同一个查询搜得准不准"，查询理解决定的是"搜没搜对东西"。

### 换了更强的检索器，为什么准确率没涨（Day 8.6）

Dense 把证据召回从 0.565 提到 0.710（Static RAG），证据全齐的题从 56 涨到 95，但 EM 从 0.320 掉到 0.300（区间 [−8.0, +4.0]，不显著）。拆开看：多出来的这些"证据齐了"的题里，只有 12 题从答错变答对，另外 27 题补上证据以后**还是答错**。

这说明瓶颈已经不在检索器上了。把错误分四类（证据是否全齐 × 是否答对）：

| Static RAG | 证据齐+答对 | 证据齐+答错（读不对） | 证据缺+答对（蒙对） | 证据缺+答错（搜不到） |
|---|---|---|---|---|
| BM25 | 26 | 30 | 38 | 106 |
| Dense | 38 | **57** | 22 | 83 |

换检索器把"搜不到"从 106 压到 83，但"读不对"从 30 涨到 57。还有一个现象：召回变高的题净赚 7 题，召回变低的题净亏 6 题，**召回没变的 113 题也净亏 5 题**——换了检索器，即使召回水平一样，给模型看的段落也换了，答案跟着变。这提醒：和"证据召回"这个中间指标比，端到端指标才是结果。

对方法的启示：V2 的自适应策略不该只盯着"怎么搜得更多"（已经够多了），要看"怎么读对、什么时候停、要不要重排"。重排（Day 9）正好是给"读不对"这一类用的：候选已经召回来了，只是顺序不对。

> **Day 9 更正**：上面"瓶颈已经不在检索器上"说过头了。加了重排以后 EM 从 0.300 涨到 0.405（4 个解码设定都显著），因为两段金标同时进前 3 的题从 95 涨到 137。Dense 提高的是"前 20 条里有没有"（召回广度），答题看的是"前 3 条里齐不齐"（头部精度），这是两回事。教训：中间指标要选和下游实际消费方式一致的那个口径。

### 重排（Rerank）：召回求全、精排求准（Day 9）

- **结构**：Cross-Encoder（交叉编码器）把（查询, 段落）拼成一条输入一起过模型，每一层注意力里查询的每个词都能看到段落的每个词，最后输出一个相关性分数。双塔（向量检索）是分开编码、最后算一次内积。
- **为什么更准、为什么不能拿来检索**：双塔要在不知道查询的情况下把整段压成一个向量；交叉编码看着查询读段落，能对上细粒度的匹配。代价是不能离线预算，每个（查询, 段落）都要现算，只能用在几十条候选上。
- **在项目里**：bge-reranker-base（XLM-RoBERTa base，12 层），GPU fp16，20 条候选约 16～22ms，显存 0.7GB；CPU 上要 0.9 秒。
- **上限是候选池**：重排只能调顺序，候选池里没有的金标救不回来。HotpotQA 上重排补上了"候选池@20 和前 3 条之间缺口"的 73～88%；2Wiki 组合题候选池@20 只有 0.57，重排之后也只到 0.55，这类题要靠改写 / 拆解问题。
- **重排抹平检索器差距**：重排前 Dense 比 Hybrid 高 2 个点、比 BM25 高 15 个点；重排后 Dense 和 Hybrid 只差 0.5 个点。只要候选池够全，选哪一路召回就不太重要了。
- **类比**：推荐里召回通道调得再细，精排模型一换，通道之间的差异就被吸收掉大半。所以资源应该先投在精排上，再看召回。

### 强基线 + 按需升级：级联（Cascade）（Day 9）

Day 9 最重要的发现：**在 Dense + 重排这个强检索下，多轮 Agent 不比只搜一次的 Static RAG 强**（EM 差距 −6.5～+3.5，4 个解码设定都不显著），成本却是 3.9 倍输入 token、5 倍延迟。

所以 V2 的问题从"Agent 怎么选检索器"变成"**什么时候值得从单次升级成多轮**"：
- 默认走便宜的强基线（搜一次 + 重排）；
- 只在信号表明需要时才升级成多轮。
- 上限：两种方法逐题取较好的一个，EM 比强基线高 8（只算稳定赢的题）～13 个点（单次运行）。
- 难点：Agent 稳定赢的 16 题里，10 题强基线已经拿到了全部证据，升级的信号不能只看"证据缺不缺"，还要看"答案确不确定"。

**类比**：搜索和推荐里的级联排序——大部分请求走轻量模型就返回，只有不确定的请求才送到重模型。省成本的关键不在重模型多好，而在"判断该不该送"的那一步准不准。


### 查询改写：改什么、看没看证据、在哪一步改（Day 10）

三组对照（检索栈统一 Dense + 重排，作答提示词一字不差，只差证据来自哪些查询）：

| 组 | 检索 | EM | 证据召回 |
|---|---|---|---|
| B3：原问题搜一次 | 原问题 | 0.405 | 0.823 |
| 静态改写代替原问题 | 模型改写 | 0.320 | 0.715 |
| 两跳：原问题 → 静态改写 | 2 次 | 0.360 | 0.833 |
| 两跳：原问题 → 证据条件改写 | 2 次 | 0.425 | 0.868 |

- **只看问题的一次性改写，比原问题差**（EM −8.5、召回 −10.8，都显著）。模型会去掉 "Which/What"、加上 "birth year"、丢掉年份，改出来的查询反而更差。V1 里"Agent 第一个查询不如原问题"不是 Agent 特有的，是这类改写本身的问题。
- **第二跳不看证据 = 白搜**（EM −4.5 显著更差）；**看了证据才有用**（召回 +4.5 显著，EM +2.0 不显著）。关键对比是"证据改写 − 静态改写 = +6.5 显著"，说明收益来自信息，不是来自多搜一次。
- **不是靠多看段落**：原问题取前 6 条（和两跳的组看到同样多的段落）和证据改写比，后者的召回仍高（不显著），因为第二跳拿到的是新证据。
- **顺带解释了 V1 的一个发现**：多轮 Agent 的证据召回（0.807）低于只搜一次的 B3（0.823），因为它第一跳就用改写过的查询，而不是原问题。

**类比**：搜索里的查询理解——纠错、改写、扩展。评估时要区分"改写让召回到了正确的文档"和"最终答案碰巧对了"，所以固定计划（每题搜几次固定）比让模型自由决定更能隔离查询这一个变量。

### 问题拆解：只看问题拆不出桥接实体（Day 10.4，2Wiki）

2Wiki 的组合题（"When did the director of film X die?"）是典型的两跳：先找到 X 的导演是谁，再查这个人的卒年。导演的名字**不在问题里**。

把金标段落分成两类：问题里点了名的实体（X 这部电影）、桥接实体（导演，名字只出现在第一跳段落里）。只搜一次原问题时，两类的召回分别是 **0.98 和 0.066**——单次检索基本碰不到第二跳。

| 组合题 | EM | 桥接实体召回 |
|---|---|---|
| B3：原问题搜一次 | 0.105 | 0.077 |
| 静态拆解：一次拆成 2 个子查询 | 0.105 | 0.077 |
| 证据改写：原问题 → 看结果再写 | **0.245** | **0.474** |

静态拆解的子查询长这样："Who is the director of the film X?" 和 "When did the director of film X die?"。两个都只能围着 X 打转，因为拆的时候还不知道导演是谁。有 4 个子查询直接写成了占位符："When was [director name] born?"——模型知道该查什么，但不知道名字。

**结论**：多跳问题的"拆解"不能一次性做完，第二步必须等第一步的结果。这就是为什么 ReAct / Search-R1 这类方法是"想一步、搜一步、看一步"的交替结构，而不是"先规划好所有查询再一起搜"。

**类比**：推荐里的序列决策——下一次推荐要依赖用户对上一次的反馈，不能一次把整个序列排好。



证据条件改写那一步，模型手里有第一跳的全部段落、提示词让它再搜一次。200 题里 **111 题（56%）直接写出了答案、拒绝再搜**：
- 这 111 题里 90 题第一跳证据已经全齐；代码把它们的第二跳退回原问题（等于又搜了一遍原问题），证据和 B3 逐条相同 → **EM 和 B3 完全一样，一次翻转都没有**。
- 另外 89 题写了第二跳查询的，只有 18 题真的补到了新金标，其中 6 题由错变对；搜错的代价是 2 题由对变错。

所以"看完第一跳，模型还想不想再搜"是一个几乎免费的升级判据：想停就停（零损失），想搜就搜（有正收益）。

**2Wiki 上复现**（800 题）：385 题拒绝再搜，EM 和 B3 完全相同；415 题写了查询，45 题错→对、13 题对→错。有一个细节：桥接比较题要 4 段金标，前 3 条不可能齐，但模型照样有 127 题拒绝再搜，EM 也没变。所以这个信号的含义是"模型觉得够答了"，不是"证据真的齐了"——对按需升级来说，前者才是需要的。它对应搜广推里的级联：先跑轻量链路，用一个便宜的判据决定要不要升级到重链路。

**代价**：升级的那一组比 B3 多一次检索 + 一次改写调用，输入 token 2.2 倍、延迟 3.6 倍。所以"该不该升级"判对一次，省下的是整组多出来的成本。

### 级联里的"探测"：一次调用同时是阅读器和路由器（Day 11.4）

按需升级（cascade）的流程：B3 先搜一次 → 门控决定要不要"探测" → 探测时把第一跳结果交给模型，问它还要不要再搜。
用 Agent 提示词探测（工具有 search 和 final_answer）时，HotpotQA 上比 B3 高 **+8.0**（显著）。拆开来看：

| 探测结果 | 题数 | B3 答对 | agent 探测答对 | 说明 |
|---|---|---|---|---|
| 直接作答 | 92 | 40 | **51** | 证据和 B3 逐字相同，只是模型自己答了 |
| 再搜一次 | 91 | 35 | 40 | 真正的"升级" |
| 格式错误 / 重复 | 17 | 6 | 6 | 退回 B3 的答案 |

所以 +8.0 ≈ **+5.5 来自"有把握时自己直接答"** + 2.5 来自"再搜一次"。

**会不会只是作答提示词写得更好？** 做了一个 2×2 对照：同一份证据，只改"证据放在哪"（用户消息 / 工具返回）和"给什么系统提示"（只能作答 / Agent）。四组里只有"工具返回 × Agent"高（+4.0，不显著），而且这 +4 全部来自模型**自己选择**直接作答的题；它想搜却被强制作答的题反而 −3。
→ 收益不是来自格式，而是来自**模型的自我选择**：有把握就答，没把握就别硬答。所以 B3 不改格式。

**两个信号不互补**：直接作答赢的 15 题里，11 题的重排分差很小，门控会放过它们。分差门控挑的是"证据不够、该再搜"的题；直接作答的收益在"证据已经够、但 B3 读错了"的题上。两个信号管的是两种不同的错误。

**类比**：级联排序里，重模型通常只负责"打分"。这里的探测除了给答案，还顺带说了"我有把握 / 我还要更多信息"，相当于让精排模型同时输出一个置信度，供路由使用。

**方法论**：诊断时复用已有运行里存下的检索结果，四组看到的段落逐字相同，差别只剩格式这一个变量；"B3 写法组和 B3 运行 200/200 逐字一致"用来证明复用没走样。

### 门控、离线推算和多 seed：按需升级怎么做得又便宜又可信（Day 11）

**门控信号：重排第 1、2 名的分差。**这个分数是重排时顺手算出来的，不用再调模型。分差大，说明只有第 1 段特别相关、第 2 段已经不沾边；多跳题需要两段证据，另一段很可能没搜到，该升级。分差小，说明好几段都相关，不用升级。它预测"升级有没有帮助"的 AUC 约 0.74，两个数据集都是这个水平。

**门槛跨数据集选（样本外）。**HotpotQA 用的门槛是在 2Wiki 上选的，2Wiki 用的是在 HotpotQA 上选的。在同一批题上选门槛再报结果，相当于拿考试题调参，结果会偏乐观。

**离线精确推算。**cascade 的设计保证"从不探测"和 B3 逐字相同、"每题都探测"和 Day 10 的两跳运行逐字相同，所以贪心解码下任何门槛的效果都能直接拼出来，不用重跑。在线实测和离线推算 200/200 一致。调门槛从"跑一次 10 分钟"变成"算一次 1 秒"。
- 前提是确定性：temperature 0 时同样的输入得到同样的输出。一旦采样就不成立了，所以多 seed 必须在线跑。

**多 seed（temperature 0.7，每个 seed 和同 seed 的 B3 配对）：**

| − B3（EM 点） | HotpotQA | 2Wiki | 成本 |
|---|---|---|---|
| 分差门控 | +1.5 / +1.0 / +1.5（0/3 显著） | +2.6 / +3.0 / +3.9（3/3） | 约 1.4 倍 |
| 每题都 agent 探测 | +6.0 / +6.0 / +2.5（2/3） | +2.0 / +6.2 / +5.2（2/3） | 约 2 倍 |

**为什么分差门控在 2Wiki 稳、在 HotpotQA 不显著？**门控只管一种错误："证据不够"。2Wiki 的升级收益几乎全来自"再搜一次补证据"（组合题的桥接实体第一跳拿不到），正好是门控挑出来的那类题。HotpotQA 的收益大头在"证据已经够、但 B3 读错了"，靠模型自己直接作答来救，这类题分差小，门控根本不会放它们去探测。再加上采样下真正再搜的题从 21% 降到 13～20%，HotpotQA 上剩下的收益就淹没在噪声里了。
→ 一个门控信号只覆盖一种错误；要覆盖"读错"，得用模型自己的把握（agent 探测），代价是每题多一次调用。

**类比**：推荐里的级联排序——粗排后只把一部分请求送进精排。省成本的关键不在精排多强，而在"送哪些"的判断准不准；而且送的判据要对准损失的来源，召回不足和排序错误要用不同的信号。

### test 集和预先登记：怎么让结论可信（Day 12）

**为什么必须留一份没碰过的 test。**Day 8～11 的检索器、重排、门槛、提示词都是在 validation 上挑的。同一批题上调方法、又在这批题上报成绩，报出来的数会偏高（也叫过拟合验证集）。所以留一份从没运行过的 test，方法定稿后只跑一次。搜广推同理：离线调参看验证集，最终效果看没参与调参的数据或线上 A/B。

**预先登记（pre-registration）。**跑 test 之前先写文件并 commit：跑哪几组、用什么门槛、怎么判定显著、什么情况才允许重跑（只有基础设施故障）。这样"看到结果再挑组"就不可能了。面试时可以直接给出 commit 时间作为证据。

**test 比 validation 更难。**2Wiki 的 B3 从 validation 的 0.346 掉到 test 的 0.299，全量多轮 Agent 的 +2.0 也缩到 +1.4。绝对水平会掉，但方法之间的相对结论（谁比谁好、贵多少）保持住了——这正是留 test 的意义。

**结果（test，和 B3 逐题配对）：**

| −B3 EM | HotpotQA | 2Wiki | 输入 token 倍数 |
|---|---|---|---|
| 全量多轮 Agent | +1.8（不显著） | +1.4（不显著） | 4.25 / 4.51 |
| cascade 分差门控 | +2.6 * | +2.8 * | 1.54 / 1.45 |
| cascade 每题 agent 探测 | +6.6 * | +7.1 * | 1.91 / 2.09 |

**按题型看两种升级各修了哪种错误**（2Wiki，每类 200 题）：B3 的短板是组合题（0.120）和推理题（0.065）。分差门控只能修组合题（→0.195，因为它是"桥接实体没搜到"这类）；agent 探测把组合题修到 0.220，还额外把比较题从 0.515 修到 0.635（这类题证据本来就够，是读错，门控看不见）。而全量多轮 Agent 反而把桥接比较题从 0.495 弄到 0.345——多搜几轮会把答案带偏。所以"多搜"不是免费的，搜什么、什么时候搜才决定收益。

**类比**：推荐系统里召回和排序各修一种错误，加一个"召回更多"的模块不会修排序错误。用哪个信号去决定"升级"，要看你想修的是哪种损失。

### 商品搜索的评测：nDCG 和"固定候选池"（Day 13）

**nDCG@10（归一化折损累计增益）**：排序指标。每个位置的商品按标签给分（E=3、S=2、C=1、I=0），越靠前权重越大（除以 log2(位置+1)），再除以"完美排序"的得分归一化到 0～1。和 QA 的 EM 不同，它关心的是**顺序**，而且允许"部分相关"（替代品 S 也有分）。
- 增益映射是**人为设定**的：互补品 C（比如搜手机出了手机壳）算不算好结果因业务而异，所以另报 C=0 的口径做敏感性分析，两种口径结论一致才可信

**Setting A vs Setting B**：
- A（固定候选池）：每个查询只排官方已标注的约 21 个商品，所有方法排同一批，比的是纯排序能力，对应搜广推里的**精排**
- B（全库检索）：在 48 万商品里检索，对应**召回**。难点是标注不完整：没标注的商品不一定不相关，**不能当负例**，只能报"已标注正例被找回了多少"

**为什么随机排序就有 0.746**：候选池是官方从真实搜索结果里挑出来标注的，大部分本来就是 E 或 S。所以这个任务的区分度在"把 E 排到 S 前面"，提升空间只有十几个点。面试时要先讲清基线和上限，再讲提升。

**领域迁移的教训**：QA 上的重排模型（bge-reranker-base）带来 +10 个点，到商品上只有 +0.8 且不显著。它是在问答 / 网页段落上训练的，商品标题短、型号和规格词多，"是不是精确匹配"不是它学过的判断。**接口能复用，不代表模型效果能迁移**，这两件事要分开报告。

### 按需升级什么时候有用：贵的一路要带来新信息（Day 13）

把 QA 上成立的级联原样搬到商品排序：便宜的一路是 Dense 排序，贵的一路是让 3B 模型给候选逐条打分再重排，门控同样用 Dense 第 1、2 名分差。结果：LLM 重排不比 Dense 好（−0.5，144 好 / 144 坏），门控信号 AUC 全在 0.5 左右。

**为什么 QA 上成立、商品上不成立：**
- QA 的"升级"是**多搜一次**：第二跳能拿到第一跳没有的桥接实体，信息量真的变多了。分差大正好代表"另一段证据没搜到"
- 商品的"升级"只是**换一个判断者**，对同一批候选重排，没有新信息进来；而且 LLM 只看标题和品牌，Dense 还看了描述。候选池里也不存在"缺证据"，分差就只是噪声
- 按 Dense 自身质量分档：Dense 排得差的查询上 LLM 略有帮助，排得好的查询上显著帮倒忙 → 把排好的列表交给更弱的判断者，只会加噪声

**类比**：推荐系统里，精排比粗排强是因为它用了更多特征（交叉特征、实时行为）。如果"精排"拿到的特征比粗排还少，送进去只会更差。级联的前提是后一级**信息更多或模型更强**，不是"调用更贵"。

**方法论**：小样本（debug 25 条）上是 +0.66，400 条上 −0.47；结果不好时没有继续调提示词，因为给全分的查询已经打平、理想上限只有 +1.7，再调就是在 validation 上找偶然的正结果。负结果照样写进报告。

### 微调商品重排模型：缺的是领域数据（Day 15）

**训练目标 ListNet（列表式损失）**：同一个查询的候选放成一组，模型给每个（查询, 商品）打一个分。目标分布 = softmax(增益)，E=3 的商品目标概率最高；损失是目标分布和 softmax(模型分数) 的交叉熵。它只关心组内相对高低，和 nDCG 的口径一致。对比两种常见做法：
- 逐点（pointwise）：把每对当成"相关 / 不相关"二分类。简单，但不直接优化排序，而且 E/S/C/I 有四档，二分类会丢信息
- 逐对（pairwise）：同组里取一正一负，让正的分数更高。是排序常用做法，但每组要采很多对
- 列表式（listwise，ListNet / LambdaRank）：一次看整组，最贴近 nDCG

**防泄漏的一个坑**：我们的 validation / debug 也是从官方 train 抽的，训练时必须先剔掉，否则就是拿考题训练。脚本里加了断言。

**结果**：test 上 +2.5（显著），收益集中在否定词（+10.7）、型号、多约束查询。向量检索把 "necklace without pendant"（不带吊坠的项链）和吊坠项链编码得很近，因为它只看整体语义相似度；Cross-Encoder 让查询和商品逐词交互，再用标签教它"without"的意思，就能分开。

**类比**：这就是搜广推里的精排模型训练——通用预训练模型 + 业务标注数据微调。通用模型解决"大致相关"，领域微调解决"业务定义的相关"（这里是 Amazon 定义的 E/S/C/I）。

**和按需升级的关系**：商品上门控依旧无效（AUC ≈ 0.5），而且重排（19ms）比 Dense 现场编码（45ms）还快——级联的价值来自"贵的一路很贵"。QA 里升级 = 多调一次 3B 大模型（约 900ms），门控才值钱；商品里重排很便宜，直接全做。

### GRPO 的显存账：为什么单卡 4090 跑不了 3B 全参（V3 评估）

全参数训练时，每个参数要存 4 份东西：fp32 权重（4 字节）、fp32 梯度（4 字节）、Adam 的一阶和二阶动量（各 4 字节），一共 **16 字节 / 参数**。3B 模型就是 49GB，比 4090 的 24GB 大一倍，这还没算激活和生成时的 KV cache。

**为什么权重必须用 fp32**：GRPO 的学习率是 1e-6。Adam 归一化后每步更新量约等于学习率，而权重本身约 0.02 量级，相对变化只有 5e-5。bf16 只有 8 位有效位，相对精度约 0.4%，这么小的更新加上去会被直接舍入掉，模型等于没训练。所以要用 fp32 存一份"主权重"，计算时再转成 bf16。

**LoRA 为什么省**：原权重冻结（bf16，6.2GB），只训练插在每层旁边的两个小矩阵（秩 16 时约 3000 万参数，状态不到 0.5GB）。GRPO 还要一个参考模型算 KL，用 LoRA 时把 LoRA 关掉就是参考模型，不用再存一份。

**生成阶段的 KV cache**：每个 token 要存每一层的 K 和 V。Qwen2.5-3B 用了分组查询注意力（GQA），只有 2 个 KV 头，每 token 只要 2 × 36 层 × 2 头 × 128 维 × 2 字节 ≈ 36KB；如果是 16 个 KV 头，就是 8 倍。

**LoRA 做 RL 会不会掉点**：Thinking Machines 的 "LoRA Without Regret"（2025-09）发现，策略梯度 RL 里 LoRA 秩取 1 都能追平全参。原因是信息量：监督学习每条样本给出"每个 token 该是什么"，信息量和 token 数成正比；RL 每条轨迹只得到一个奖励分数，约 1 bit，需要学的东西少，低秩就够。三个前提：LoRA 要加在所有层（只加注意力层会学不动）、学习率约为全参的 10 倍、batch 不宜太大。监督微调则不同，数据量超过 LoRA 容量时会落后于全参。

**类比**：和推荐模型训练一样，显存大头往往不在"模型本身"，而在优化器状态和中间结果（推荐里是巨大的 embedding 表和它的 Adam 状态，所以常用稀疏优化器或只给活跃 ID 更新）。

### 换卡噪声：贪心解码为什么换了显卡就不一样（迁移验收，2026-10-06）

**现象**：同样的代码、数据、配置，B3 在 4090 上 EM 0.405，在 A800 上 0.390。200 题里 9 题答案不同，其中 8 题模型看到的证据一模一样。A800 上自己重跑一次，200 题逐字相同。

**原因**：浮点加法不满足结合律，(a+b)+c 和 a+(b+c) 在 bf16 / fp16 下结果可能差最后一位。不同显卡的矩阵乘法用不同的分块和累加顺序（cuBLAS / FlashAttention 按硬件选不同的实现），所以 logit 有极小差异。贪心解码每步取概率最大的词，平时这点差异不影响，但遇到两个候选词概率几乎一样的位置（比如是非题里的 `yes` 和 `true`），就可能选了不同的词，后面的生成就全变了。同一张卡、同一个实现，累加顺序固定，所以同机重跑逐字一致。检索这边同理：Dense 索引在新卡上重新编码，分数差约 1e-4，只让近似并列的段落换了位置。

**对项目的影响**：比较两个方法时，"什么都不改、只换环境"本身就能带来约 1.5 个点的 EM 变化。所以 V3 的 RL 模型必须和在同一台机器上重跑的对照组比，不能拿 4090 上的旧数字当对照。

**类比**：推荐系统的线上 A/B 前先做 A/A 实验，两组流量用同一个策略，先看指标自然波动有多大，再判断 B 组的提升是不是真的。这次的同机重跑就相当于 A/A，换卡对比相当于"换了机房的 A/A"。

## 面试问答

**问：简单讲讲 Search-R1 是怎么做的？**
答：它把检索当成环境交互的一步：模型写出搜索标签时暂停，由外部循环执行检索、把结果拼回上下文，再继续生成。训练时检索内容只参与前向计算、不参与损失，因为它不是策略的动作，不遮会让模型学会编造文档。奖励只看最终答案，靠 GRPO 组内对比把功劳分到中间的搜索决策上。缺点是奖励没有成本项，模型不会学"少搜"，这是我做自适应搜索的出发点。

**问：你的 Agent 怎么处理模型输出格式错误？**
答：分四层校验：语法（能否解析）、结构（工具名和参数是否合法）、策略（重复查询、超预算）、执行（工具超时）。每层有独立的错误码，错误信息作为观察结果拼回给模型让它改正，同时计入轮数预算防止死循环，并写进日志统计格式有效率。解析只看本轮新生成的内容，训练、评测、推理共用同一个解析器。

**问：Agent 和 Static RAG 你是怎么保证比较公平的？**
答：三点口径统一。① 同一个 Budget 定义，`top_k` 由配置固定，不交给模型；② 所有方法用同一个解析器和答案提取规则，Direct 相当于搜索上限为 0 的 Agent；③ 成本按实际执行的检索次数算，停止原因按"自己作答 / 被预算截停 / 没作答"拆开报告，避免强制作答掩盖停止能力。

**问：Agent 反复搜同一个东西怎么办？**
答：两层。执行前做 query 归一化（大小写、标点、空白），命中就拦下，不扣搜索次数但扣轮数，由 `max_turns` 兜底；不做语义去重，因为误拦正当改写的代价比漏放重复大。执行后统计本轮新文档数，只记录不拦截，既能发现"换了说法的重复"，也是后面自适应停止的边际收益特征。

**问：你的 Mock 环境怎么保证不泄漏？**
答：检索工具的接口只收 query 和 top_k，拿不到题目 ID 和标准答案，物理上读不到标签；语料用虚构实体，模型没法凭记忆作答；检索确定性（同分按 doc_id 排序），测试可复现。

**问：你怎么测试 Agent？测试全过就说明 Agent 能用吗？**
答：分两类。控制逻辑用按剧本输出的假模型测，结果完全确定，覆盖四层错误、预算记账、强制作答时机、防泄漏，还故意改坏关键设计确认测试能失败。但这只证明管道没漏：剧本只覆盖我们想得到的错误，也验证不了模型能力。能力要接真模型，在 validation 上看格式有效率、错误分布，并人工抽查轨迹；语料用虚构实体，答对只可能是用了检索结果。

**问：为什么不直接在提示词里告诉模型剩余预算？**
答：V1 不告诉，因为会干扰核心测量：forced_answer 变少可能只是模型会数数了，而且有锚定效应，简单题也会把预算用满。但它本身是一种零成本的自适应策略，类似广告的预算平滑，所以我把它作为 V2 的对照基线：复杂的路由和停止策略如果连它都比不过，就不值得做。

**问：你的实验怎么保证可复现？**
答：每次运行保存代码版本、完整配置、运行环境、每道题的完整轨迹；代码没提交就拒绝运行，调试时强制运行会另存改动并在目录名上标记。模型服务出错的题不丢掉，计 0 分留在分母里，同时报告失败率，超过 2% 判这次运行无效，避免难题被悄悄移出分母导致准确率虚高。

**问：你的检索语料是什么？为什么不用全量维基？**
答：用 HotpotQA 所有题目自带段落组成的语料池，约 50 万段，所有方法共用同一个池子，并在实验表里标注这是语料池设定、不是全量维基。选它是为了迭代快：前期要反复调策略、画预算曲线，全量维基的索引和评测都慢一个量级。池子由整个数据集决定，不依赖抽到哪些测试题。后期会在全量维基上做鲁棒性验证。

**问：为什么需要多轮搜索？有数据支撑吗？**
答：有。我做过检索体检：拿原问题搜一次，前 3 条能找齐两段金标证据的只有 28%，桥接题前 20 条也只有一半。原因是第二跳的实体不在问题里，比如问"芝麻街的原始执行制片人"，答案所在段落的人名只有读了芝麻街那一段才知道。而比较题两个实体都在问题里，一次搜索就能找到大部分证据。所以多轮是必要的，而且不同题需要的轮数不同，这就是自适应分配的依据。

**问：检索内容为什么要做 loss mask？**
答：策略梯度只对策略自己采样的动作有定义，检索 token 是环境给的。不遮的话，正优势会让模型学会自己续写文档（幻觉），负优势会惩罚本身没错的真实文档。mask 只作用在损失上，模型前向时仍能看到检索内容。

**问：BM25 是怎么打分的？和向量检索比有什么优缺点？**
答：BM25 对查询里的每个词算三件事再求和：词越稀有权重越高（IDF），词在段落里出现越多分越高但有饱和上限（k1），长段落要打折（b）。优点是专有名词精确匹配强、不用训练、CPU 上 50 万段 10ms 级、结果确定可解释；缺点是只认字面，同义词和不同说法对不上。我在语料池上实际遇到过：搜 "Mary Gordon birth year"，正确段落写的是 "born"，BM25 反而把圣母诞生那段排在前面。所以 V1 用 BM25 做固定检索器研究 Agent 本身，V2 再加向量检索做多路召回，让 Agent 按题选择检索路径。

**问：让 Agent 自己写查询，一定比直接用原问题搜好吗？**
答：不一定，我有个实测的例子。比较题 "Mary Gordon 和 H. L. Mencken 谁出生更早"，模型把查询拆成 "Mary Gordon birth year"，拆分本身是对的，因为前 3 名放不下两个实体。但 birth 和维基原文的 born 对不上，Mencken 的简介甚至没有 born，只写了生卒年；单独搜 Mencken 时，他妻子、父亲、故居的段落提到他的次数比他本人简介还多，金标从第 5 掉到第 8。改成 "实体名 + 类型词"（H. L. Mencken journalist）就回到第 2。结论是查询要写成文档会怎么写，而且查询好坏要用证据召回量，不能凭直觉。这和工业 Query Rewrite 是同一个问题：把用户说法对齐到物料侧的说法。

**问：你的基线怎么设计的？Agent 比 Static RAG 好多少？**
答：四种设定共用同一个循环、解析器、预算和评测器：Direct 不给证据，Static RAG 拿原问题搜一次给前 3 条，Agent 自己决定搜什么、搜几次，另外加一个 Oracle 诊断，直接给金标段落，衡量证据完美时的阅读上限。前三者只能作答的提示词一字不差，只差证据。在 200 道验证题上，EM 分别是 0.12、0.32、0.35、0.54。搜一次提升 20 个点，最划算；Agent 再多 3 个点，但逐题配对的 bootstrap 区间跨过 0，不显著，成本却是 4 倍 token。我拆了原因：Agent 自己改写的第一个查询比原问题更差的有 26 题、更好的只有 8 题，多轮的收益全靠多搜。另外 Oracle 只有 54%，阅读和答案格式的损失比检索还大。所以固定地多搜不划算，应该按题目决定花多少算力、花在检索还是阅读上，这是我 V2 的出发点。

**问：第一次检索固定用原问题、之后再让 Agent 改写，是不是只赚不亏？**
答：直觉上像，但数据告诉我没有这个保证。支持它的证据：原问题一次就找齐证据的题占 28%，这些题上 Agent 自己改写后准确率 0.38，反而低于直接用原问题的 Static RAG（0.46）；而且模型找齐证据后 78% 会立刻停，所以简单题上既能回分又能省成本，第一轮还省掉一次写查询的模型调用。但有三个风险：一是预算挤占，搜索上限 3 次时已有 45 题用满，原问题占一个名额，难题上模型自己能用的搜索就少了一次，就像多路召回里给原始 query 保底一路，就挤占了改写路的 quota；二是有 8 题模型改写得比原问题好，第一轮会变差；三是贪心解码有路径依赖，第一轮看到的东西变了，后面整条轨迹都会变。唯一有数学保证的是证据召回不低于 Static RAG，因为召回是所有检索结果的并集，但准确率没有这种单调性，多给的上下文也可能干扰阅读。所以我把它当成一个消融，在同等预算下和其他策略比，而不是默认它更好。

**问：你怎么处理模型输出格式不稳定？放宽解析不会掩盖问题吗？**
答：原则是只在意图没有歧义时放宽，范围要窄，而且每次放宽都在轨迹里打标记、在指标里计数。比如模型把 JSON 写完整了，后面跟了几个乱码 token，又没写结尾标签。我只取第一个完整的 JSON，这和停止词"只执行第一个动作"的口径一致；而纯文字写出的答案我仍然不接受，因为那会把"模型没按格式说话"记成"模型决定停下"。收益我是用离线重放算的：轨迹里存了每轮原始输出，拿新解析器重新解析一遍就知道救回了几题。结果只有 +0.5 个点，救回的 5 题只有 1 题答对。同时我试过另一个改动，把报错换一种消息角色发回，结果 Agent 没收益，Direct 反而变差，我就回退了。一次只改一个变量，才分得清收益来自哪。

**问：看轨迹发现了什么？和你 V2 的设计有什么关系？**
答：我看了 10 条多轮轨迹，每个现象再全量计数，不凭个例下结论。最重要的是白搜：约 9% 的搜索一篇新文档都拿不到，常见是在旧查询后面加 "more detailed" 这种词，BM25 的结果根本不变；6% 的搜索发生在证据已经齐了之后；还有 21 题搜索次数用完了还想搜，比如比较题把 3 次全花在一个实体上，另一个一次没搜。这对应推荐里的边际收益递减：同一路召回反复拉，新物料越来越少。所以"这次搜索带来了多少新文档"和"剩余预算"是我 V2 决定是否继续搜的核心信号。另一个发现是答案形式，13% 的题答案和金标互相包含但 EM 记 0 分，比格式修复多一个量级，这是便宜的提分点。

**问：搜索拿不到新文档时让 Agent 直接停下，是个好规则吗？怎么验证？**
答：我用现有轨迹离线算过，不划算。验证集上触发这条规则的有 30 题，但只能省 9 次搜索，占 2.4%，因为大部分"没新文档"本来就发生在最后一次搜索；而有 4 题之后其实还能找到新的金标证据，其中 2 题最终答对了，停下会误伤。更重要的是另外 19 题：证据没齐，之后也没找到，说明拿不到新文档往往不是信息找完了，而是这条查询路子卡住了，比如把几个词堆在一起搜。这时候该换路，拆成子问题或者换向量检索，就像推荐里某一路召回连着几刷没有新物料，应该把名额切给别的召回路，而不是停止整个召回。工程上还要注意，检索超时和检索成功但没新结果要分开记，否则规则会被超时误触发。验证我分三层：先用已有轨迹做离线反事实初筛；再对触发的题做前缀重放，原样重放到触发那一轮后强制作答，贪心解码下这就是精确的反事实，只要几十次调用；最后才在同等预算下跑完整消融，准确率和成本一起报。

**问：你怎么做错题分析？Agent 主要错在哪？**
答：每道错题只归一个主因，规则是"改哪一处最可能让它变对"，从最便宜的修复开始判断：先看是不是格式或答案写法问题，再看证据够不够，证据够了就是阅读问题；证据不够再看是停早了、查询写得差、白搜浪费了预算，最后才算检索器能力不够。只归一个主因，各类加起来才等于错题总数，才能回答先修哪个。结果是 Agent 的 129 道错题里，阅读侧占 57%，搜索行为占 30%，检索器能力只占 9%；而只搜一次的 Static RAG，检索器能力的错误有 83 题。也就是说多轮搜索把搜不到基本解决了，但错误转移成了读不对和停太早，所以净提升只有 7 题。分类规则我人工抽查过 21 条，17 条一致，不一致的主要是第一跳读错导致后面走偏、别名和答案粒度，这类规则判不出来。

**问：多轮搜索把检索错误从 83 题压到 12 题，最后只多对 7 题，那多轮到底有没有用？Static RAG 是不是就够了？**
答：有用，但要看对指标。多轮的价值在召回端，把"搜不到"的错误基本解决了，这是实打实的。EM 上只多 3.5 个点、不显著，是因为错误转移到了下游。一部分是答案写法：把只是写法不同的答案也算对，贪心解码下差距是 8 个点、区间 [+1, +15]；但换 3 个采样 seed 重跑，只有一个 seed 显著，所以这个优势不稳。真正稳的是证据召回：4 种解码设定下 Agent 都比 Static RAG 高 8.5 到 12.5 个点，全部显著。另一部分是证据里的干扰和停止决策：有 10 道题不检索能答对，检索后反而被干扰段落带偏；还有 29 题停早了。这和推荐里召回率涨了、点击率没涨是一回事，问题通常在排序和展示，而不是召回本身。所以结论不是 Static RAG 就够了，而是只加召回不够，下游的阅读、重排和停止要一起优化，这是我 V2 的方向。至于换更大的模型，它会让所有方法一起涨，证明不了多轮范式本身的价值；而且阅读侧的错误里一半是写法问题，改提示词就能修，不用换模型。

**问：你的错题分类是人工标的还是模型标的？**
答：都不是，是代码规则。对每道错题按固定顺序问一串是非问题，第一个回答"是"的就是主因，顺序从最便宜的修复开始：格式、答案写法、证据够不够，证据不够再看是停早了、查询差、白搜，最后才是检索器能力。只用轨迹和答案文件，完全可复现。我人工核对了 21 条，17 条一致，规则判不出来的是"找到了但理解歪了"、别名和答案粒度，要用大模型当裁判才能判，但裁判也有偏差，所以只作诊断。

**问：你怎么确认方法间的差距不是随机波动？**
答：两层。第一层是逐题配对 bootstrap：同一道题两种方法的得分相减，再对这 200 个差值重采样算区间，比两组独立比较更敏感，因为题目难度的差异被抵消了。第二层是解码波动：主结果用贪心解码，但贪心只是把随机性固定住了，没有消除它，我试过改一句和搜索无关的提示词，77% 的题搜索路径都变了。所以我又用温度采样跑了 3 个 seed。结果是证据召回的优势在所有设定下都显著，但 EM 的差距在 −2 到 +4.5 之间、符号会翻，说明 V1 只能说"多轮稳定地提高了召回"，不能说"提高了准确率"。另外 Agent 有 28% 的题换一个 seed 结果就变，Static RAG 只有 6%，因为多轮每轮都采样，差异沿轨迹累积。从 V2 开始，我所有的方法比较都报贪心加 3 个 seed，多数 seed 显著才算显著。

**问：怎么让 Agent 知道自己什么时候该多搜？**
答：一个信号是采样一致性，同一道题采样几次，答案都一样说明模型比较确定。我用 3 个 seed 验证过：3 次一致的题准确率 56%，全不一致的是 0%，校准得很好，而且不一致的题证据召回也更低。但它只能发现问题，分不清问题在哪：证据齐了还读错的题有 77% 也不一致，这时候多搜没用；而 3 次一致的题里也有将近一半是自信地答错。所以我不直接用"不确定就多搜"，而是和证据侧的信号组合：不确定而且证据缺，才继续搜；不确定但证据已经够了，就换成重排或重读；确定就停。成本上也不能整条轨迹跑多遍，只在作答那一步用 vLLM 的 n 参数并行采样几个短答案，同一个上下文只预填充一次，或者直接读答案的 token 概率。这和推荐里按不确定性做探索是一个思路，前提是多探索确实能让估计变准。

**问：你调过提示词吗？效果怎么样？**
答：调过一次答案规范，比如是非题只答 yes/no、人名用文档里的全名。单轮的 Direct 涨了 6 个点、显著，但 Agent 掉了 6 个点。拆开有两个原因：一是 HotpotQA 金标的写法本身不一致，有的用全名有的用常用名，要求全名修对一批又改错一批；二是对多轮 Agent 没有局部改动，这段说明在系统提示词里，每轮都看得到，改完 77% 的题搜索路径都变了，变差的 24 题里 20 题是轨迹变了，不是答案写法变了。所以我回退了，也不再逐条调提示词，因为在 Agent 上调提示词等于在噪声里调参。这让我意识到，多轮系统的改动要看整条轨迹的影响，不能只看改动的那一处。

**问：检索一定有帮助吗？**
答：不一定。我对比过不检索和检索的逐题结果：有 10 道题模型不检索能答对，Agent 检索之后反而答错了，其中 6 道是金标证据都拿到了，还是被同一批结果里的其他段落带偏。反过来检索救回了 57 道题，所以净效果是大幅正向，但说明多给证据有代价，就像推荐里召回太多低质物料会稀释排序效果。另一个例子是 BM25 的排序偏差：问"自杀森林是哪片森林"，Aokigahara 的简介里明明写着 Suicide Forest，但它是长文档、只提一次，以它为题材的电影页面反而排在前面。这类问题要靠重排解决，而不是多搜。

**问：vLLM 为什么快？你项目里怎么用的？**
答：两个核心技术。PagedAttention 把 KV cache 像内存分页一样按块按需分配，不按最大长度预留，显存利用率高，同时能跑的请求多；continuous batching 每生成一步就重新组批，写完的请求马上换成新请求，GPU 不空等。我的项目里它是独立的模型服务，Agent 通过 OpenAI 兼容接口调用，每轮记录服务端返回的输入输出 token 数。我实测过，单轮延迟基本由输出长度决定，每个输出 token 约 9ms，输入 token 几乎不影响延迟，因为预填充是并行的。但多轮 Agent 每轮都要重读全部上下文，输入 token 随轮数线性累加，占了总 token 的九成以上，这是算力成本的大头，所以我把输入输出 token 分开统计。

**问：接真模型时遇到过什么问题？**
答：Qwen2.5-3B 的工具调用格式有效率一开始是 0/8，查询意图没问题，但写成了模仿提示词字面的格式。换成它微调时见过的原生工具说明后是 8/8。结论是不训练的模型要迁就它的训练格式，就像线上特征格式要和训练时一致。另一个问题是模型会一轮写多个调用，还没看到检索结果就先作答，我用停止词在第一个调用结束处截断，把"每轮一个动作"交给代码强制，而不是靠提示词劝说。接进完整循环后又发现，第一轮格式全对，出错都在看到检索结果之后：模型先写一段推理，再写调用时 JSON 写完就结束，漏了结尾标签。我没有整体放宽解析，只放宽了这一种没有歧义的情况，并在轨迹里打标记，格式错误率从 18% 降到 4%。

**问：BM25 和向量检索各自擅长什么？你的数据上谁更好？**
答：BM25 匹配"提到"，向量检索匹配"关于"。在 HotpotQA 验证集上，拿原问题搜一次，向量检索的前 3 条召回是 71%，BM25 是 57%。比较题差距最大，98% 对 59%：比较题点名了两个实体，很多段落都会提到这个实体，BM25 按词频把"提到"的段落排前面，向量检索能找到"讲的就是它"的介绍段。BM25 赢的 20 段全是桥接题，问题里有个罕见名字只出现在另一个实体的段落正文里，向量把整段压成一个向量，这个词就被稀释了。还有个反直觉的结果：向量检索只搜一次，就超过了 BM25 Agent 搜多轮，说明召回质量本身比多搜几次更重要。但这个结论要打折扣，e5 预训练用过维基的（标题, 段落）对，和这个数据集的形式几乎一样，换到商品搜索要重新验证。

**问：混合检索为什么用 RRF？混合一定比单路好吗？**
答：两路分数量纲不同，BM25 没有上界，余弦挤在 0.7 到 0.9，直接相加等于 BM25 说了算，加权得先校准。RRF 只看名次，不用校准，是多路融合最常用的无参基线。但混合不一定更好：我的数据上等权 RRF 没超过单独的向量检索，比较题上还掉了 12 个点，因为 BM25 比向量检索弱很多，等权会把它排错的段落拉进前排。融合要有用，两路得水平相近又互补。混合只在前 20 条召回略高，所以我把它当候选池，顺序交给后面的重排模型。

**问：你的 Agent 能自适应选检索器，这个收益有多大？**
答：我先量了上限，而不是直接做路由器。做法是每道题事后挑召回最高的那一路，相当于一个完美的路由器。在 HotpotQA 上它只比"永远用向量检索"多 5.5 个点，2Wiki 上多 3.4 个点，因为 57% 到 70% 的题两路打平。真实路由器一般只能拿到上限的一半，就落到噪声范围里了，所以我把"选检索器"降成了一个小消融，没有当卖点。反倒是查询构造的影响大得多：同样在 2Wiki 上，用整句问题去搜召回是 59%，换成"实体 + 关系"这种拆好的子查询是 97%。所以我把主线转到了查询改写和问题拆解上。另外一个发现是最强的检索器依数据集而变，HotpotQA 上是向量检索，2Wiki 上是混合检索，所以强基线不能写死，要按数据集挑。

**问：你为什么要加重排？效果怎么样？**
答：加了向量检索以后，前 20 条里基本都有金标，但两段金标同时进前 3 的题不多，而模型只看前 3 条。重排就是用一个更准的 Cross-Encoder 把这 20 条重新排一遍。它把查询和段落拼在一起过模型，能对上细粒度的匹配，代价是不能预先计算，只能用在几十条候选上，这和推荐里召回加精排的分工一样。效果：一次重排 16ms 左右，前 3 条召回涨 11 到 17 个点，单次检索的准确率从 30% 涨到 40.5%，4 个解码设定都显著。一个附带发现是重排把检索器之间的差距抹平了，向量和混合重排后只差半个点，所以选哪一路召回没那么重要了。

**问：多轮 Agent 在你的实验里到底有没有用？**
答：要看和谁比。和 BM25 单次检索比，多轮能多找到证据；但检索换成向量加重排之后，只搜一次的基线准确率就到 40.5%，多轮 Agent 是 39%，4 个解码设定都不显著，成本却是 4 到 5 倍。所以我没有硬说"Agent 更好"，而是把问题改成了"什么时候值得从单次升级成多轮"。两者逐题取较好的一个能到 53%，说明升级是有空间的，难点在判断。我发现 Agent 稳定赢的题里一大半，单次检索其实已经拿到了全部证据，所以升级信号不能只看"证据够不够"，还要看答案的不确定性，比如多次采样的答案一致性。这就是推荐里的级联：大部分请求轻量返回，只把不确定的送到重模型。

**问：查询改写有用吗？**
答：要分开看。我做了三组公平对照：只让模型看一眼问题就改写、然后拿改写代替原问题去搜，这一组比直接用原问题差 8.5 个点，召回也低 11 个点，统计显著。改写的模型会去掉疑问词、加一些它觉得相关的词、丢掉年份，反而更差。但在多轮里，让第二跳的查询看到第一跳的检索结果，然后搜第二个实体，这一组比原问题单次检索高 4.5 个点召回，显著。关键对照是"看证据的改写"减"不看证据的改写"，多 6.5 个点，显著，所以收益来自信息而不是多搜一次。这也顺带解释了我之前发现的一个反常现象：多轮 Agent 的证据召回低于只搜一次的基线，因为它第一跳就用改写过的查询。

**问：你说按需升级，具体怎么判断该不该升级？**
答：最有效的一个判据很便宜：让模型手里拿着第一跳的检索结果，问它"再搜一次吗"。200 道题里 111 道它直接给答案、拒绝再搜，这 111 道的证据和只搜一次的基线逐条相同，准确率一模一样，一次翻转都没有。剩下 89 道它愿意再搜，其中 18 道真的补到了新证据，6 道因此答对，搜错的代价只有 2 道。所以"想不想再搜"几乎是免费的判据。这也对应推荐里的级联：大部分请求走轻量链路，只把不确定的送重模型。

**问：改写提示词时你踩过什么坑？**
答：同一个模型，同一份证据，只是摆放方式不同，效果差很多。第一版我把段落放在用户消息里告诉它"已经搜到这些，再写一个查询"，50 道题里它一次都没用上段落里的实体，几乎都在复述原问题。改成 Agent 的对话格式——把它之前那次检索写成它自己发出的工具调用、结果以工具返回的形式给它——用上证据里实体的比例升到 22%。不训练的模型在工具调用这类格式上，只认它微调时见过的样子。这个坑在接模型那天（Day 3）已经遇到一次，这次是同一个道理的另一个侧面。

**问：问题拆解（Query Decomposition）有用吗？**
答：我在 2Wiki 的组合题上专门测过。这类题像"某部电影的导演是什么时候去世的"，导演的名字不在问题里，只出现在第一跳搜到的电影页里。我把金标段落分成"问题里点了名的"和"桥接实体"两类：只搜一次原问题，前者召回 98%，后者只有 6.6%。让模型一次性把问题拆成两个子查询再分别搜，组合题的准确率和召回一点都没涨，因为拆的时候它还不知道导演是谁，子查询只能围着电影名打转，有几个甚至直接写成了"[director name]"这种占位符。换成先搜一次、让模型看了结果再写第二个查询，组合题准确率从 10.5% 涨到 24.5%，桥接实体召回从 7.7% 涨到 47%。所以多跳问题的拆解不能一次规划完，第二步必须等第一步的结果，这也是 ReAct 这类交替结构存在的原因。

**问：你的按需升级里，收益到底来自"多搜一次"还是别的？**
答：我专门拆过。用 Agent 提示词做探测，HotpotQA 上比强基线高 8 个点。按探测结果分组配对之后发现，一大半收益不来自再搜：92 道题模型看完第一跳就直接作答，证据和基线逐字相同，却多答对了 11 道。我怀疑只是作答提示词写法不同，就做了一个 2×2 对照，同一份证据只改证据摆放位置和系统提示。结果单纯换格式不显著，收益全部集中在模型自己选择作答的题上，它想搜却被强制作答的题反而变差。所以结论是：模型对"自己能不能答"的判断本身就是一个有用的信号，而且这个信号和我用的重排分差门控管的是两种错误，前者救"证据够了但读错"，后者救"证据不够"。这也是我没去改基线作答格式的原因，改了不显著，还会动到所有对照组。后来在 2Wiki 上复查，"直接作答"的收益只剩 2 个点左右，换格式反而显著变差 4 个点；而"再搜一次"的收益两个数据集都稳定在 2.3～2.5 个点。所以真正能迁移的是"缺证据时再搜"。

**问：重排分差门控是怎么来的？可信吗？**
答：门控决定哪些题值得多花一次模型调用。我用的信号是重排第 1、2 名的分差：分差大说明只有一段特别相关，多跳题的另一段多半没搜到。这个信号零成本，预测"升级有益"的 AUC 约 0.74。可信度上我做了三件事。一是门槛跨数据集选，HotpotQA 用 2Wiki 上选的门槛，反过来也一样，避免在同一批题上调参。二是把系统设计成和已有运行逐字等价，贪心下可以离线精确推算任何门槛，在线复核 200/200 一致。三是用 3 个采样 seed 复查，每个 seed 和同 seed 的基线配对。结果是 2Wiki 上 3 个 seed 都显著（+2.6～+3.9，成本只多 40%），HotpotQA 上 3 个 seed 都为正但都不显著。原因是这个信号只抓"证据不够"，而 HotpotQA 的收益主要来自"证据够了但读错"。

**问：最后你的按需升级到底推荐哪个方案？**
答：它给的是一条质量–成本曲线，不是单个点。要省钱用分差门控，只探测三成的题，输入 token 约基线的 1.4 倍，两个数据集都是正收益，2Wiki 上稳定显著。要质量就每题用 Agent 提示词探测一次，约 2 倍 token，平均高 5 个点左右，两个数据集都是 3 个 seed 里 2 个显著。全程让 Agent 自己多轮搜，成本约 4 倍，准确率反而不如基线，被两者都比下去了。

**问：你怎么保证你的提升不是调参调出来的？**
答：三道防线。第一，所有阈值、提示词、检索器选择都只在 validation 上定，test 集从建好到方法定稿一次都没跑过。第二，定稿后我把要跑的组、用的门槛、显著性的判定和"只有基础设施故障才能重跑"写进预先登记文件并 commit，再跑 test，test 每组只跑一次。第三，门槛不是在本数据集上选的，是拿另一个数据集选出来的门槛直接用的。结果是三条预期在 test 上全部成立：分差门控在两个数据集上都显著（+2.6 / +2.8，成本 1.5 倍左右），每题 agent 探测 +6.6 / +7.1（约 2 倍成本），而全量多轮 Agent 不显著、贵 4 倍以上。

**问：为什么不对所有 Query 都让 Agent 多搜几轮？**
答：因为在我的实验里它不划算，而且原因可归因。全量多轮 Agent 输入 token 是基线的 4.25～4.51 倍，EM 只高 1.4～1.8 个点且不显著。按题型拆开：它在组合题上确实有用（0.120 → 0.280），但把桥接比较题从 0.495 弄差到 0.345，净收益接近 0。所以不是"搜得多"没用，而是"不加区分地搜"没用。我改成先搜一次拿证据，再用零成本信号（重排第 1、2 名的分差）只给约三成的题追加一次探测，就能拿到 2.6～2.8 个点、成本只多 45～54%。

**问：你的按需升级方法换到商品搜索上还有效吗？**
答：我专门试了，没有效果，而且能解释原因。在商品排序上，便宜的一路是向量检索，贵的一路是让 3B 模型给前 20 个候选逐条打相关性分再重排。400 条查询上 LLM 重排比向量检索还低 0.5 个点，变好变差各 144 条；QA 上好用的分差信号，在这里预测"升级有没有用"的 AUC 只有 0.51。原因是两边的"升级"本质不同：QA 里升级是多搜一次，能拿到第一跳没有的证据；商品排序里升级只是换一个判断者重排同一批候选，没有新信息，而且模型只看了标题和品牌，比向量检索看到的还少。所以结论是：级联有用的前提是后一级能带来新信息或者更强的判断能力，而不是调用更贵。工程接口是复用成功的，策略效果没有迁移，这两件事我在报告里分开写。

**问：你在商品搜索上最后有什么正结果吗？**
答：有。一开始我把 QA 上的检索栈原样搬过去，通用的向量模型、重排模型和 3B 大模型在商品上全部打平，nDCG@10 都在 0.85 左右，我的判断是缺的不是方法而是领域数据。于是用 ESCI 官方训练集的 2 万条查询和 E/S/C/I 标签微调重排模型，训练目标用列表式的 ListNet，和 nDCG 一样只看组内顺序。为了防泄漏，验证集是从官方训练集里抽的，训练前先剔掉了。检查点固定用最后一步，在 test 上预先登记后只跑一次：比向量检索高 2.5 个点、显著，耗时没变。拆开看，收益集中在含否定词的查询上，比如"不带吊坠的项链"，高了 10 个点，向量检索只看整体语义，分不清否定。这也说明了按需升级不是万能的：商品上重排只要 19 毫秒，比向量检索还快，没有成本可省，直接全做就是最优；QA 上升级要多调一次大模型，门控才值钱。

**问：你中途换过机器，怎么保证前后实验可比？**
答：换机前我写了恢复脚本，所有模型、原始数据、语料和划分都用 sha256 校验，数据准备脚本重跑后和原来逐字节一致；检索不比索引文件，比 500 条查询的检索结果，BM25 完全一致，Dense 前 3 名完全一致，只有第 4 名以后近似并列的段落换了位置。然后做了换卡复现性检查：同一个基线在新旧两张卡上贪心解码，200 题有 9 题答案不同，EM 差 1.5 个点，而新卡上自己重跑是逐字一致的。所以我的做法是旧结果照常引用，但 RL 之后的新模型一律和在新卡上重跑的对照组比，这样同机比较没有换卡这层噪声，比 1.5 个点小的差别我也不会声称是提升。
