## Day 1 思考题

1. ReAct 里的"思考"步骤不会改变外部环境，为什么它还有用？
   - 我的回答：思考有多种作用，如把复杂任务拆成多个子目标分步执行、搜索之后总结材料、规划下一步、异常判断等，可以克服只推理（CoT-only）和只行动（Act-only）两种模式的局限。
   - 点评（✅ 基本到位）：回答了"思考能做什么"，还要补上"为什么有用"的机制——
     - 模型下一步动作只取决于上下文。思考不改变环境，但改变**模型自己的上下文**（工作记忆），后面的动作以写下来的中间结论为条件。论文写法：动作空间扩成 Â = A ∪ L，思考是语言空间里的动作，只更新上下文、不触发环境反馈。
     - 计算量角度：Transformer 每个 token 的计算量固定，写出推理过程 = 用更多 token 换更多串行计算。
     - 代价：思考花 token 和时延。"什么时候值得思考 / 搜索"本身就是算力分配问题，正是本项目"自适应"要解决的。
     - 类比：搜索系统里的 Query 理解模块，本身不返回商品，但决定后面走哪路召回、怎么改写。
2. 为什么检索回来的内容要从训练损失里遮掉？不遮会怎样？
   - 我的回答：检索内容属于观察，来自搜索引擎，不在模型能改变的范围内。如果不遮，搜索引擎返回的 token 很多，真正需要算损失的部分会被淹没，模型得不到有效更新。
   - 点评（⚠️ 方向对，主要理由要纠正）："淹没"只是次要因素，就算检索内容很短也照样要遮。问题出在梯度方向，不在大小：
     - **数学上没意义**：策略梯度 ∇J = E[Σ A_t · ∇log π(a_t|s_t)] 只对策略自己采样的动作求和；检索 token 是环境写进来的，对它们算 log π 再乘优势没有意义。PPO 的重要性比率同理。
     - **会学歪**：不遮 = 训练模型在 `<information>` 后面自己续写文档。优势为正时，模型学会编造检索结果（幻觉），甚至不调搜索直接脑补；优势为负时，又压低了真实文档的概率，引入噪声。
     - **易混点**：遮的只是梯度，前向计算时模型仍然能看到检索内容（`loss_mask` 不影响注意力）。
     - 你说的"淹没"体现在 `ray_trainer.py:864` 的 `state_tokens/coverage`（模型自己生成的 token 占比）上，但它是附带问题。
3. 奖励只看最终答案对不对，模型是怎么学会"该搜什么、什么时候搜"的？
   - 我的回答：模型在 PPO 过程中会学到哪些步骤或思考方式最终能得到正确答案，然后强化这种能答对的做法。
   - 点评（⚠️ 太笼统）：这说的是结果，没讲机制。核心问题是**信用分配**（credit assignment）：奖励只在最后给一次，怎样传到中间的搜索词上？
     - **探索是前提**：RL 只能强化采样里出现过的行为。基座模型从来不搜，给多少奖励也学不会。
     - **组内对比（GRPO）**：同一题采 5 条轨迹，A_i = (r_i − 组内均值) / 组内标准差。答对轨迹里所有模型生成的 token（搜索标签、搜索词、`<answer>`）都被提高概率，答错的被压低。同题几条轨迹往往就差在"搜没搜、搜了什么"，所以信号正好落在这些决策上。PPO 则靠价值模型加 GAE 把奖励往前分摊。
     - **统计累积**：单条轨迹很噪，但跨大量题目平均后，只有和答对稳定相关的决策会被强化。
     - 类比：广告里的**转化归因**；GRPO 组内归一化 ≈ 按同一请求分组做 listwise 比较，消除题目难度偏差。
     - 本项目切入点：`qa_em.py` 的奖励没有成本项，模型只学"怎样答对"，不学"怎样用最少的搜索答对"。
4. 对照 `infer.py`：谁负责让模型停下、谁去执行搜索、谁把结果拼回去？
   - 我的回答：`StopOnSequence` 负责停下，`search(query: str)` 执行搜索，`curr_search_template` 负责拼回去。
   - 点评（✅ 正确）。补充：
     - 停下有两种：`StopOnSequence`（L31-50，遇到 `</search>` 暂停去搜）和 EOS 判断（L109，答完退出）。比较的是 token id，所以 L83 要列 6 种 `</search>` 写法（带空格或换行时 BPE 分词结果不同）。
     - 解析是 `get_query`（L52-59），拼回是 L125-126 的 `prompt += search_text`。每轮都把整个 prompt 重新编码、从头计算，不复用 KV cache。
     - 隐患：① `while True` 没有轮数上限；② `get_query` 在包括 prompt 在内的整段文本上找最后一个 `<search>`，而 prompt 自带 `<search> query </search>` 示例，生成被截断时会拿旧查询或 "query" 去搜，静默出错；③ `requests.post` 没有超时和异常处理；④ 空查询也照搜。→ 分别对应 1.3～1.5 的 Budget、解析范围与异常返回格式、空结果测试。

### 1.3 思考题（写 `agent/parser.py` 之前要定下来）

1. 模型本轮没写 `<tool_call>`，直接输出一段话。当成最终答案，还是当成 `no_action` 错误？
   - 我的回答：不清楚。
   - 讲解：
     - 宽松（当答案）：EM 拿整句去比照样错，占不到便宜；更糟的是"I need to find…"这种话也会被当成"模型决定停下"，**污染停止决策的统计**。
     - 严格（当错误）：报错拼回给模型，下一轮改正；多花一轮生成但不花搜索次数（所以 `max_turns` 和 `max_search_calls` 要分开）。风险：模型格式差时，分数反映的是"不会写格式"而非"不会搜"。
     - 公平性：Search-R1 `qa_em.py` 的 `extract_solution` 要求 `<answer>` 至少 2 个才取最后一个，因为 prompt 里有示例 `<answer> Beijing </answer>`。和 `get_query` 同一个毛病，补丁很脆弱（prompt 删掉示例 → 所有正确答案被丢掉）。**所有方法必须共用同一套答案提取规则**，否则差距可能来自提取规则而不是策略。类比：A/B 实验两组埋点口径不一致。
     - 决定：严格；Direct / Static RAG 也通过 `final_answer` 作答（Direct = 搜索上限为 0 的 Agent）；轨迹保存原始输出，离线算宽松诊断指标，量化"因格式损失的分"；先严格，看数据再放宽。
2. 轮数用完了还没作答：直接判 0 分，还是再给一轮"只许答"的机会？
   - 我的回答：可能选第二种好一点，总体准确率略高，也会增加平均搜索次数。
   - 点评（✅ 选对了，"增加搜索次数"要细看）：
     - 强制轮禁止搜索，**实际执行**的检索次数不变；增加的是生成 token 和时延。
     - 但 Search-R1 的统计确实会多算：强制轮（`generation.py` L296-304，`do_search=False`）模型写了 `<search>` 仍记 `is_search=1`，计入 `valid_search_stats`，实际没执行。→ 要分开记"尝试次数"和"实际执行次数"，成本按实际执行算。**口径不同，数字就不同。**
     - 强制作答会掩盖"模型是自己知道该停，还是被预算截停"。按 `stop_reason ∈ {answered, forced_answer, no_answer}` 拆开报告；`forced_answer` 占比本身就是自适应停止要优化的指标。
     - 比 Search-R1 更明确的两处：① 强制轮占 `max_turns` 的最后一轮（Search-R1 是额外 +1 轮），保持硬上限；② 明确告诉模型"最后一轮、只能作答"（Search-R1 靠 RL 从奖励里学会这条规则；不训练就只能写进上下文）。

### 1.4 思考题（写最小循环之前要定下来）

1. Mock 检索工具为什么要做成确定性的？如果在 mock 里直接放进 gold 段落或答案，会有什么问题？
   - 我的回答：模拟真实检索引擎，对相同 query 返回相同内容。如果直接放 gold 段落，模型会误以为所有 query 都能返回标准答案，就学不到该怎么写 query 了。
   - 点评：
     - 前半句结论对、理由要换：真实检索不一定确定（索引更新、向量检索是近似的、同分文档顺序会变，所以 plan Day 2 要"固定相同 Query 的 TopK 顺序"）。真正原因是**可复现 + 控制变量**：测试失败能复现；方法间差距不能来自检索波动；轨迹能从 JSONL 重放。类比：离线评估固定样本和特征快照、A/B 实验只让策略不同。
     - 后半句在 **RL 训练场景（V3）完全正确**：环境总返回 gold，策略学到"随便搜都行"。但 V1 不训练，更直接的问题是：① 答案是喂进去的，准确率失真，测试因为错误的原因通过；② mock 要返回 gold 就得读标签，代码里留下泄漏通道。
     - 防泄漏靠接口签名：`search(query, top_k)` 拿不到题目 ID，物理上读不到标签。
     - 区分：语料**包含**答案是正常的；问题是工具**根据标签挑结果**。旧 `hotpotqa_corpus.jsonl` 是否只有 gold 段落，是同一问题的放大版（Day 2 核查）。
2. 怎样才算"重复"查询？被拦下的要不要扣搜索预算？
   - 我的回答：只差大小写/空格比较好；完全相同会有遗漏，语义判断成本高、不好判断。
   - 点评（✅ 选择和推理都对）：
     - 判定原则：检索器认为一样就算重复。BM25 分词会丢标点，所以标点也要归一化。类比：查缓存前的 query 归一化。
     - 语义去重最大的风险是**误判**：`Tessa Marrow` vs `Tessa Marrow birthplace` 语义接近，但后者是正当的追加限定词。误拦一次可能答错，漏放一次只多花一次搜索 → 宁可漏判，不可误判。
     - 补充：执行后看结果重合度（`num_new_docs`），只记录、不拦截。零成本抓到"换了说法的重复"，也是 V2 自适应停止的特征（边际收益）。类比：多路召回按 item id 去重。
     - 预算（没答的半题）：没执行 → 不扣搜索次数；这一轮生成花了 → 扣轮数；`search_attempts` +1。拦截本身几乎零成本，成本在模型白生成了一轮；`max_turns` 兜底防死循环。

### 1.5 思考题（写冒烟测试之前）

1. 用假模型（`ScriptedLLM`）做测试，能验证什么、不能验证什么？冒烟测试全过，能不能说"Agent 能用"？
   - 我的回答：能测试整体流程是否跑通，不能验证 LLM 相关的结论，如是否能理解检索结果并正确使用。冒烟测试通过后，还要确认检索结果是否正常、模型能否理解检索结果并输出正确答案。
   - 点评（✅ 核心判断对）：
     - 精确说法：它验证的是**控制逻辑**（预算记账、错误路由、停止原因、报错是否拼回），确定的逻辑用确定的输入测。
     - 另外两类盲区：① 剧本是我们编的，只覆盖**想得到**的错误（和黑名单同一个盲点），真模型怎么写错只有真跑才知道；② 接口没验证：`role="tool"` 在 Qwen 模板里的实际渲染、真实检索的时延和失败方式。
     - 还缺的证据（Day 3）：小 validation 集上的格式有效率、错误类型分布、人工抽查轨迹（虚构语料 → 答对只能是用了检索结果）。
     - 类比：排序服务的单元测试证明管道没写错，效果要靠离线评估和 A/B。
2. 要不要在每轮观察里告诉模型"还剩几次搜索"？
   - 我的回答：不太清楚，直观感觉没必要。告诉之后 forced_answer 可能更少，比较可能不太公平。
   - 点评（⚠️ 结论对，理由要换）：
     - 区分**公平**和**干扰测量**。公平 = 资源和评分口径相同；Static RAG 没有决策，告诉它预算没意义，所以不存在不公平。真正的问题是干扰测量：forced_answer 变少，可能是模型会数数了，而不是会判断"信息够了"，弄脏核心指标。
     - 副作用：① 锚定效应，把预算当目标、简单题也搜满（年底突击花预算）；② 提示词随预算变化，`Budget ∈ {1,2,3,5}` 曲线分不清是资源多了还是提示词不同。
     - 但它确实是一种策略：类比广告**预算平滑（budget pacing）**，出价器知道剩余预算来调节奏。→ 作为 V2 的**零成本对照基线**：花大力气做的路由/停止策略连它都比不过，就不值得做。
     - 决定：V1 不告诉；V2 作为消融项，届时再加开关。

   - 我的回答：先重试，设最大重试次数，超过之后就跳过。

## 概念卡片

### 工具调用 = 约定的文字格式 + 外部控制循环

模型只会输出文字。`infer.py` 里模型写到 `</search>` 时，由停止条件打断生成，外部程序解析出搜索词、调用检索、把结果用 `<information>` 包好拼回输入，再让模型继续写。

### 思考 = 只改上下文、不改环境的动作

ReAct 把动作空间扩成 Â = A ∪ L。思考不触发环境反馈，但把中间结论写进上下文，后续动作以它为条件；同时用更多 token 换更多串行计算。代价是 token 和时延。

### 检索内容遮罩：遮梯度，不遮注意力

策略梯度只对策略自己采样的动作有定义。检索 token 是环境写进来的，参与前向计算，但不进损失。不遮会让模型学会自己编文档。

### 结果奖励 + 组内对比 = 信用分配

只在最后给一次奖励（EM）。GRPO 在同一题的多条轨迹间做归一化，答对轨迹的每个生成 token（包括搜索决策）一起被强化。前提是模型能探索到正确行为；缺点是奖励没有搜索成本项。

### 动作校验分四层，每层各自报错

| 层 | 检查什么 | 错误码 |
|---|---|---|
| 语法层 | 能否从文字里解析出一个动作 | `no_action` / `invalid_json` |
| 结构层 | 工具名和参数是否合法 | `unknown_tool` / `invalid_args` |
| 策略层 | 合法但不该执行 | `duplicate_query` / `budget_exceeded` |
| 执行层 | 工具本身出错 | `tool_error` |

"检索成功但没结果"不是错误（`ok=True, docs=[]`）。类比：召回为空和召回服务超时是两种不同的告警。

### 动作格式：标签负责定位和停止，JSON 负责内容

采用 Qwen2.5 原生的 `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`。训练、评测、推理共用同一个解析器，避免 train-serve skew（线上线下不一致）。

### `agent/schema.py` 的三个设计决定

1. 数据结构（schema）和文字格式（parser）分开放，换格式只改解析器。
2. "停止作答"也是一个动作（`final_answer`）：每轮恰好一个动作，"何时停"被显式记录，才能统计和优化（Cost-aware Stop）。
3. `top_k` 由配置固定，不交给模型：保证和 Static RAG 拿到同样多的证据，比较才公平。
4. 补充：`Budget`（上限，放进 config.yaml，创建后不可改）和 `BudgetState`（用量，写进轨迹）分开；`max_turns` 连写错格式的轮次也算，是防死循环的硬上限，`max_search_calls` 才是实验里要权衡的成本。

### 解析严格 + 口径统一

- 纯文字不当答案（严格）；所有方法共用同一个解析器和答案提取规则。宽松指标只作为离线诊断。
- 解析器只管语法层和结构层；策略层在循环里，执行层在检索网关里。
- 一轮写多个 tool_call：只执行第一个（与 Search-R1 训练代码一致），个数 `num_tool_calls` 记进轨迹。

### 停止原因要拆开记

`stop_reason ∈ {answered, forced_answer, no_answer}`。强制作答提高准确率，但会掩盖模型会不会自己停；`forced_answer` 占比是自适应停止的核心指标。搜索次数分"尝试"和"实际执行"，成本按实际执行算。

### 1.4 最小循环的几个设计点

- **防泄漏靠接口**：检索工具只收 `query, top_k`；`qid` 只进轨迹用于对齐。
- **Mock 语料用虚构实体**：接真模型后它没法凭记忆作答，答对就说明确实用了检索。
- **模型接口只有"给消息、返回文字"**：测试用 `ScriptedLLM`（按剧本输出，完全确定），Day 3 换真模型不改循环。
- **强制作答的时机**：只在"最后一轮"或"模型在搜索次数用完后仍想搜"之后；搜索次数刚用完时不提前强制。这样 `forced_answer` 统计的才是"还想搜但被截停"。
- **三个计数**：`turns_used`（每轮都算）、`search_attempts`（想搜就算）、`search_calls_used`（实际执行才算，含超时）。成本按最后一个算。
- **检索出错**：算一次实际执行（请求已发出），但不记入"已搜过"，允许原样重试。

### 测试要能失败才有意义（改坏检查）

测试第一次就全绿，不能说明它有效。故意把关键设计改坏（本项目：解析范围、查询归一化），看对应测试能否抓到。1.5 里就靠这个发现：`test_prompt_example_is_never_executed` 原先设 `max_turns=1`，唯一一轮是强制作答轮，误解析出的搜索会被预算拦下、根本不执行，测试只是碰巧靠错误码抓到 → 改成默认预算。
这个做法叫 mutation testing（变异测试）；类比：检验监控告警，要故意注入故障看它响不响。

### 冒烟测试的分工

- `test_action_schema.py`：语法层和结构层（纯文字、截断、非法 JSON、未知工具、空查询、多写参数）+ Budget 校验和不可修改。
- `test_mock_search.py`：检索确定性（同查询同结果、同分按 doc_id、零命中返回空）。
- `test_loop.py`：策略层和执行层（重复查询、超预算、强制作答时机、轮数用完、空结果、检索出错）+ `infer.py` 回归测试 + 防泄漏 + 轨迹可以序列化后原样读回。
- 运行：`pytest tests/`，或 plan 验收命令 `python -m tests.test_action_schema`。

### BM25：词匹配打分（Day 2）

- 分数 ≈ 查询词在段落里出现得多（词频，有饱和上限 k1）× 这个词在全库里稀有（IDF）÷ 段落长度（长段落会被惩罚，参数 b）。
- 擅长人名、地名、专有名词的精确匹配；不懂同义改写（"创始人"和"创立者"对不上）。这正是 V2 要加向量检索、做混合检索的原因。
- 类比：搜索里的倒排召回（关键词召回），向量检索对应语义召回，两者合起来就是多路召回。

### 证据召回：把"搜得好不好"和"答得好不好"分开（Day 2）

- `evidence_recall`：整条轨迹检索到的段落，覆盖了几个金标段落。`all_evidence_found`：金标全部找齐的比例。
- 答错可能有两种原因：没搜到证据（检索问题），或搜到了但没读懂（模型问题）。只看准确率分不开。类比：推荐系统里分别看召回率和排序 AUC，才知道瓶颈在召回还是排序。

### 检索体检的发现：为什么需要多轮、为什么需要自适应（Day 2）

- 原问题搜一次，前 3 条找齐两个金标：28%。桥接题前 20 条也只有 50%：第二跳实体（如 "David Connell"）不在问题里，只有读了第一跳（"Sesame Street"）才知道。
- 比较题两个实体都在问题里，一次搜索前 20 条能找齐 85%。
- → 多轮搜索有必要；不同类型的题需要的搜索量不同，这就是自适应分配搜索算力的依据。

### 语料池 vs 全量维基（Day 2）

- 语料池 50.7 万段（HotpotQA 所有题目自带的段落），全量维基约 520 万段。池子小一个量级，检索更容易，**实验表必须标注 `retrieval_setting=pool`**，不能说成开放域全库检索。
- 池子由整个数据集决定、不依赖抽到哪些题，所有方法用同一个池子，比较仍然公平。
- 后期扩容后用全量维基做鲁棒性验证：结论在更难的检索设定下是否仍然成立。

### Search-R1 源码里的几个关键点

- 检索内容遮罩：`search_r1/llm_agent/generation.py` 的 `info_mask` → `verl/trainer/ppo/ray_trainer.py:859` 的 `loss_mask`。
- 奖励：`verl/utils/reward_score/qa_em.py` 只看最终答案是否与标准答案完全一致（EM）；`format_score` 默认 0，没有成本项。
- 答案提取：`extract_solution` 在整段文本上找 `<answer>`，少于 2 个返回 None（为了跳过 prompt 里的示例），很脆弱。
- 强制作答轮：`max_turns` 之后再加一轮 `do_search=False`；这一轮的 `<search>` 仍计入 `valid_search_stats`。
- 训练配置：`train_grpo.sh` 默认 8 卡、每批 512 条、每题采样 5 条轨迹为一组（`n_agent=5`）、最多搜 2 轮（`max_turns=2`）。

## 面试问答

**问：简单讲讲 Search-R1 是怎么做的？**
答：它把检索当成环境交互的一步：模型写出搜索标签时暂停，由外部循环执行检索、把结果拼回上下文，再继续生成。训练时检索内容只参与前向计算、不参与损失，因为它不是策略的动作，不遮会让模型学会编造文档。奖励只看最终答案，靠 GRPO 组内对比把功劳分到中间的搜索决策上。缺点是奖励没有成本项，模型不会学"少搜"，这是我做自适应搜索的出发点。

**问：你的 Agent 怎么处理模型输出格式错误？**
答：分四层校验：语法（能否解析）、结构（工具名和参数是否合法）、策略（重复查询、超预算）、执行（工具超时）。每层有独立的错误码，错误信息作为观察结果拼回给模型让它改正，同时计入轮数预算防止死循环，并写进日志统计格式有效率。解析只看本轮新生成的内容，训练、评测、推理共用同一个解析器。

**问：Agent 和 Static RAG 你是怎么保证比较公平的？**
答：三点口径统一。① 同一个 Budget 定义，`top_k` 由配置固定，不交给模型；② 所有方法用同一个解析器和答案提取规则，Direct 相当于搜索上限为 0 的 Agent；③ 成本按实际执行的检索次数算，停止原因按"自己作答 / 被预算截停 / 没作答"拆开报告，避免强制作答掩盖停止能力。

**问：Agent 反复搜同一个东西怎么办？**
答：两层。执行前做 query 归一化（大小写、标点、空白），命中就拦下，不扣搜索次数但扣轮数，由 `max_turns` 兜底；不做语义去重，因为误拦正当改写的代价比漏放重复大。执行后统计本轮新文档数，只记录不拦截，既能发现"换了说法的重复"，也是后面自适应停止的边际收益特征。

**问：你的 Mock 环境怎么保证不泄漏？**
答：检索工具的接口只收 query 和 top_k，拿不到题目 ID 和标准答案，物理上读不到标签；语料用虚构实体，模型没法凭记忆作答；检索确定性（同分按 doc_id 排序），测试可复现。

**问：你怎么测试 Agent？测试全过就说明 Agent 能用吗？**
答：分两类。控制逻辑用按剧本输出的假模型测，结果完全确定，覆盖四层错误、预算记账、强制作答时机、防泄漏，还故意改坏关键设计确认测试能失败。但这只证明管道没漏：剧本只覆盖我们想得到的错误，也验证不了模型能力。能力要接真模型，在 validation 上看格式有效率、错误分布，并人工抽查轨迹；语料用虚构实体，答对只可能是用了检索结果。

**问：为什么不直接在提示词里告诉模型剩余预算？**
答：V1 不告诉，因为会干扰核心测量：forced_answer 变少可能只是模型会数数了，而且有锚定效应，简单题也会把预算用满。但它本身是一种零成本的自适应策略，类似广告的预算平滑，所以我把它作为 V2 的对照基线：复杂的路由和停止策略如果连它都比不过，就不值得做。

**问：你的实验怎么保证可复现？**
答：每次运行保存代码版本、完整配置、运行环境、每道题的完整轨迹；代码没提交就拒绝运行，调试时强制运行会另存改动并在目录名上标记。模型服务出错的题不丢掉，计 0 分留在分母里，同时报告失败率，超过 2% 判这次运行无效，避免难题被悄悄移出分母导致准确率虚高。

**问：你的检索语料是什么？为什么不用全量维基？**
答：用 HotpotQA 所有题目自带段落组成的语料池，约 50 万段，所有方法共用同一个池子，并在实验表里标注这是语料池设定、不是全量维基。选它是为了迭代快：前期要反复调策略、画预算曲线，全量维基的索引和评测都慢一个量级。池子由整个数据集决定，不依赖抽到哪些测试题。后期会在全量维基上做鲁棒性验证。

**问：为什么需要多轮搜索？有数据支撑吗？**
答：有。我做过检索体检：拿原问题搜一次，前 3 条能找齐两段金标证据的只有 28%，桥接题前 20 条也只有一半。原因是第二跳的实体不在问题里，比如问"芝麻街的原始执行制片人"，答案所在段落的人名只有读了芝麻街那一段才知道。而比较题两个实体都在问题里，一次搜索就能找到大部分证据。所以多轮是必要的，而且不同题需要的轮数不同，这就是自适应分配的依据。

**问：检索内容为什么要做 loss mask？**
答：策略梯度只对策略自己采样的动作有定义，检索 token 是环境给的。不遮的话，正优势会让模型学会自己续写文档（幻觉），负优势会惩罚本身没错的真实文档。mask 只作用在损失上，模型前向时仍能看到检索内容。
