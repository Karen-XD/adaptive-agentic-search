## 1. 一句话：项目要回答什么问题

> Agent 能不能根据问题、已有证据和剩余预算，**动态决定怎么搜、要不要重排、什么时候停**，在质量接近固定强基线的前提下**减少检索成本**？这套策略能不能迁移到商品搜索？

**为什么值得做**：Search-R1 证明了模型能学会"边想边搜"，但它的奖励只看答案对不对，不管搜了几次，简单题也可能多搜。本项目补的就是**成本**这一块。

**和搜广推的关系**：本质是**算力分配**问题。

| 本项目 | 搜广推里的对应 |
|---|---|
| BM25 / 向量检索 / 混合检索 | 多路召回 |
| Reranker（重排序模型） | 精排 |
| 决定走哪路检索、要不要重排 | 按请求难度分配召回和精排算力 |
| 决定什么时候停 | 边际收益递减时停止加算力 |
| 质量-成本曲线 | 效果-延迟 / 效果-机器成本权衡 |

## 2. 整体怎么运转：一道题的一生

```text
题目（只有问题文本，没有标准答案）
   │
   ▼
┌─────────────── Agent 循环（agent/loop.py）───────────────┐
│  提示词 + 历史  →  模型生成一轮文字                          │
│                     │                                     │
│                     ▼                                     │
│  解析器（agent/parser.py）：文字 → 动作；格式错就报错给模型     │
│                     │                                     │
│                     ▼                                     │
│  策略检查：预算够不够？是不是重复查询？                         │
│                     │                                     │
│          ┌──────────┴──────────┐                          │
│       search(query)       final_answer(answer) ──→ 结束   │
│          │                                                │
│          ▼                                                │
│  检索工具（retrieval/）→ 检索结果作为"观察"拼回上下文 ──→ 下一轮  │
└───────────────────────────────────────────────────────────┘
   │
   ▼
评测器（evaluation/）：此时才读标准答案，打分
   │
   ▼
outputs/runs/<run_id>/：配置、代码版本、指标、每道题的完整轨迹、错题表
```

## 3. 路线图：三个版本

| 版本 | 时间 | 目标 | 面试时能讲什么 |
|---|---|---|---|
| **V1** | Day 1～7 | 三个基线能跑、可复现、可公平比较：Direct（不搜）、Static RAG（固定搜一次）、Vanilla Agent（自己决定搜几次） | 多轮 Agent 相比固定 RAG 好在哪，靠什么证明 |
| **V2（主体）** | Day 8～17 | 加入多路检索和重排；自适应路由和停止策略 vs 固定强漏斗（总是混合检索 + 重排）；迁移到商品搜索 | 同等质量下省了多少成本，靠哪些决策省的 |
| V3（可选） | Day 18～21 | 用 GRPO 训练搜索策略，奖励里加成本项 | 成本奖励会不会让模型干脆不搜 |

## 4. 贯穿全项目的三条原则（面试高频）

1. **口径统一，比较才公平**：所有方法共用同一个预算定义、同一个解析器、同一个评测器。检索条数由配置固定，不交给模型决定。
2. **防泄漏靠结构，不靠自觉**：检索工具的接口只收查询词，拿不到题目编号；只有评测器能读标准答案。
3. **可复现**：每次运行都记下代码版本、配置、数据、环境；代码没提交就拒绝运行。

## 5. 进度

### Day 1：最小闭环（✅ 已完成）

| 步骤 | 做了什么 | 为什么 | 结论 |
|---|---|---|---|
| 1.1 读文献 | 读 ReAct、Search-R1 论文和 `infer.py` | 项目在 Search-R1 框架上做改进，要先知道它怎么运作、缺什么 | ① 工具调用 = 约定的文字格式 + 外部控制循环；② Search-R1 奖励没有成本项，这是本项目的切入点；③ `infer.py` 有 4 个隐患（没有轮数上限、解析范围错、没有异常处理、空查询照搜），我们的设计逐条避开 |
| 1.2 环境 | 确认环境分工，补装 pytest | 模型服务和项目代码分开，避免破坏 RL 依赖 | `verl_env` 跑模型服务和 RL，`dsr1` 跑项目代码 |
| 1.3 定接口 | 定义两个动作（搜索 / 作答）、四层错误类型、预算 | 这是整个项目的"接口合同"：后面换检索器、换模型、换到商品搜索，都不改它 | 采用 Qwen 原生工具调用格式；解析严格，所有方法共用一个解析器 |
| 1.4 最小循环 | 用假检索跑通"问题 → 动作 → 观察 → 答案" | 先用确定的假零件验证控制逻辑，再换真零件，出问题时好定位 | 能正确记账、报错、在预算用完时强制作答 |
| 1.5 测试 | 40 个自动测试 | 控制逻辑对不对，要能自动证明，以后改代码也不怕改坏 | 能证明"管道不漏"，不能证明"模型好用"，后者要等 Day 3 接真模型 |
| 1.6 实验入口 | 一条命令跑完"配置 → 运行 → 评测 → 落盘" | 之后所有实验（基线、消融、预算曲线）都走这个入口，保证可复现、可比较 | 首次运行成功，5 个文件齐全；准确率 0.2 没有意义（规则假模型），只证明流程通了 |

## 6. 现在怎么运行

```bash
conda activate dsr1
cd /root/adaptive-agentic-search

pytest tests/                                                # 40 个测试
python -m evaluation.run_eval --config configs/mock_v1.yaml  # 跑一次实验（要求代码已提交）
```

一次运行会在 `outputs/runs/<时间>-<名字>/` 下生成：

| 文件 | 内容 | 用途 |
|---|---|---|
| `config.yaml` | 完整配置 + 运行环境 | 复现 |
| `git_commit.txt` | 代码版本 | 复现 |
| `metrics.json` | 准确率、失败率、平均搜索次数、格式错误率、停止原因分布 | 出实验表 |
| `trajectories.jsonl` | 每道题每一轮的动作、检索结果、耗时、预算用量 | 错题分析、重放 |
| `errors.csv` | 没答对的题，按"答错 / 没作答 / 模型服务出错"分类 | 错题分析的入口 |

## 8. 面试一分钟版（随进度更新）

> 我做的是一个自适应的 Agentic Search。出发点是 Search-R1 这类方法只奖励答对，不考虑检索成本，简单题也会多搜。我的思路类似搜广推里的算力分配：让 Agent 根据问题和已有证据，动态决定走哪路检索、要不要重排、什么时候停。
>
> 工程上我先搭了一个可复现的评测框架：所有方法共用同一套预算定义、动作解析器和评测器，保证比较公平；检索工具的接口拿不到题目编号，只有评测器能读标准答案，从结构上防止泄漏；每次实验都记录代码版本、配置和完整轨迹，可以逐题重放、做错题归因。
>
> （Day 7 后补：三个基线的对比结果；Day 14 后补：自适应策略省了多少成本。）
