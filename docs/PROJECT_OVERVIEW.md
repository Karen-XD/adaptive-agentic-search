## 0. 用的什么数据

| 数据 | 用途 | 说明 |
|---|---|---|
| **HotpotQA**（主） | 多跳问答：每道题要串起 2 个段落才能答 | 最能体现多轮搜索的价值；自带金标段落标注，能衡量"搜没搜到证据" |
| HotpotQA 语料池 | 检索的范围 | 50.7 万段（训练集 + 开发集所有题目自带的段落）。**不是全量维基**，实验表必须标注；全量维基（520 万段）留到后期做鲁棒性验证 |
| Amazon ESCI | V2 商品搜索迁移 | 商品查询 + 相关性标注 |

## 1. 一句话：项目要回答什么问题

> Agent 能不能根据问题、已有证据和剩余预算，**动态决定怎么搜、要不要重排、什么时候停**，在质量接近固定强基线的前提下**减少检索成本**？这套策略能不能迁移到商品搜索？

**为什么值得做**：Search-R1 证明了模型能学会"边想边搜"，但它的奖励只看答案对不对，不管搜了几次，简单题也可能多搜。本项目补的就是**成本**这一块。

**和搜广推的关系**：本质是**算力分配**问题。

| 本项目 | 搜广推里的对应 |
|---|---|
| BM25 / 向量检索 / 混合检索 | 多路召回 |
| Reranker（重排序模型） | 精排 |
| 决定走哪路检索、要不要重排 | 按请求难度分配召回和精排算力 |
| 决定什么时候停 | 边际收益递减时停止加算力 |
| 质量-成本曲线 | 效果-延迟 / 效果-机器成本权衡 |

## 2. 整体怎么运转：一道题的一生

```text
题目（只有问题文本，没有标准答案）
   │
   ▼
┌─────────────── Agent 循环（agent/loop.py）───────────────┐
│  提示词 + 历史  →  模型生成一轮文字                          │
│                     │                                     │
│                     ▼                                     │
│  解析器（agent/parser.py）：文字 → 动作；格式错就报错给模型     │
│                     │                                     │
│                     ▼                                     │
│  策略检查：预算够不够？是不是重复查询？                         │
│                     │                                     │
│          ┌──────────┴──────────┐                          │
│       search(query)       final_answer(answer) ──→ 结束   │
│          │                                                │
│          ▼                                                │
│  检索工具（retrieval/）→ 检索结果作为"观察"拼回上下文 ──→ 下一轮  │
└───────────────────────────────────────────────────────────┘
   │
   ▼
评测器（evaluation/）：此时才读标准答案，打分
   │
   ▼
outputs/runs/<run_id>/：配置、代码版本、指标、每道题的完整轨迹、错题表
```

## 3. 路线图：三个版本

| 版本 | 时间 | 目标 | 面试时能讲什么 |
|---|---|---|---|
| **V1** | Day 1～7 | 三个基线能跑、可复现、可公平比较：Direct（不搜）、Static RAG（固定搜一次）、Vanilla Agent（自己决定搜几次） | 多轮 Agent 相比固定 RAG 好在哪，靠什么证明 |
| **V2（主体）** | Day 8～17 | 加入多路检索和重排；自适应路由和停止策略 vs 固定强漏斗（总是混合检索 + 重排）；迁移到商品搜索 | 同等质量下省了多少成本，靠哪些决策省的 |
| V3（可选） | Day 18～21 | 用 GRPO 训练搜索策略，奖励里加成本项 | 成本奖励会不会让模型干脆不搜 |

## 4. 贯穿全项目的三条原则（面试高频）

1. **口径统一，比较才公平**：所有方法共用同一个预算定义、同一个解析器、同一个评测器。检索条数由配置固定，不交给模型决定。
2. **防泄漏靠结构，不靠自觉**：检索工具的接口只收查询词，拿不到题目编号；只有评测器能读标准答案。
3. **可复现**：每次运行都记下代码版本、配置、数据、环境；代码没提交就拒绝运行。

### Day 3：接入真模型（✅ 已完成）

| 步骤 | 做了什么 | 为什么 | 结论 |
|---|---|---|---|
| 3.1 模型服务 | 用 vLLM 把 Qwen2.5-3B 部署成 OpenAI 兼容接口（和检索服务一样是独立进程） | 模型只加载一次、多实验共用；以后换模型或多卡只改服务端 | 单次调用 130～440ms，首个请求要预热 |
| 3.2 看原始输出 | 8 道调试题，看模型怎么写动作 | 不训练的模型会不会按我们的格式说话，是后面所有实验的前提 | **格式有效率：自己写的工具说明 0/8，换成 Qwen 微调时见过的原生工具说明 8/8**，说明不训练时要顺着模型的训练格式来；模型会一轮写多个调用、没看到结果就先作答，所以生成到 `</tool_call>` 就截断，用代码强制"每轮一个动作" |
| 3.3 真模型接入 | 模型客户端（每轮记输入输出 token、延迟、截断原因）、原生提示词进代码、运行配置记下模型目录和服务端软件版本 | 基线和后面所有实验都通过它调模型；成本从这里开始按轮记录，这是"用多少算力换多少准确率"的另一半 | 端到端跑通。**第一轮格式全对，出错全在看到检索结果之后**：模型先写一段推理，再写调用时常漏掉结尾标签。解析器只放宽这一种没有歧义的情况，格式错误率 18% → 4%。另外：输入 token 随轮数累加（第 1 轮约 300，第 5 轮约 2000），**多轮的主要成本是反复读上下文，不是生成** |
| 3.4 基线 | 四种方法共用一个入口：B0 Direct（不搜）、B1 Static RAG（原问题搜一次）、Agent（自己搜）、Oracle（直接给金标段落，诊断上限，不是方法） | 基线是所有改进的参照；Oracle 把"答错"拆成检索损失和阅读损失，告诉我们算力该加在哪 | debug 50 题（不出结论）：EM 0.16 → 0.24 → 0.28 → 0.52（Oracle）。**桥接题**：Agent 0.22、Oracle 0.53，瓶颈在检索；**比较题**：Static RAG 0.50 已经等于 Oracle，Agent 反而掉到 0.43，瓶颈在阅读和答案规范。Agent 的输入 token 是 Static RAG 的 4 倍、P50 延迟 6 倍。→ **不同题型该花的算力不一样**，这正是自适应的依据 |
| 3.5 正式基线 | 人工看轨迹修了报错提示；在 validation 200 题上跑四种方法 | debug 50 题的差距容易被噪声淹没；基线表是后面所有改进的参照 | **EM：Direct 0.12 → Static RAG 0.32 → Agent 0.35 → Oracle 0.54**。搜一次 +20 个点，最划算；Agent 再 +3 个点但**不显著**（95% 区间 [−3.5, +9.5]），成本却是 4 倍 token、6.6 倍延迟。Agent 自己改写的第一个查询比原问题**更差**（变差 26 题、变好 8 题），多轮的收益来自多搜。Oracle 只有 0.54，说明**阅读损失（46 个点，含答案格式）比检索损失（19 个点）还大** |

### Day 4：Vanilla Agent 加固（✅ 已完成）

| 步骤 | 做了什么 | 为什么 | 结论 |
|---|---|---|---|
| 4.1 格式加固 | 解析器只取工具调用里第一个完整 JSON（后面的乱码丢掉并记录）；参数值里有没转义的引号时按固定骨架取值 | validation 上 Agent 8 题因为格式没作答；和停止词"只执行第一个动作"的口径对齐 | 没作答 8 → 3，**EM 只 +0.5 个点**（救回的 5 题只有 1 题答对）。离线重放旧轨迹就能精确算出这个收益，不用重跑 |
| 4.2 一个被否掉的改动 | 试过把解析报错改成普通用户消息发回 | 解析失败时没有"工具返回"，包成工具结果有点误导 | Agent 没收益，Direct 的重试反而变差 → 回退。**一次只改一个变量**，才分得清收益来自哪 |
| 4.3 人工看轨迹 | 看了 13 条（10 条真多轮），每个现象再全量计数 | 把"答错"拆成可修的动作，不凭个例下结论 | 见下方三条 |

4.3 的三条主要发现（都是 V2 的依据）：
1. **白搜**：376 次搜索里 9% 一篇新文档都没拿到（常见是在原查询后面加 "more detailed" 之类的词，BM25 结果不变），6% 发生在证据已经齐了之后；还有 21 题搜索次数用完了还想搜（例：比较题 3 次全花在一个实体上，另一个一次没搜）→ **"这次搜索的边际收益"和"剩余预算"是 V2 停止 / 路由策略的核心信号**
2. **答案形式**：26 题（13%）答案和金标互相包含但 EM 记 0（"River Calder" vs "Calder"），比格式修复救回的多一个量级 → 答案规范是便宜的提分点，要在 validation 上调
3. **靠记忆答对**：Agent 答对的题里 5% 答案不在任何检索结果里，模型是靠预训练知识答的 → EM 会略微高估检索能力，报表要同时报证据召回

另外两个"查了但不改"的：近似重复查询只漏过 1 次，不放宽去重；原地打转（连写同一句）只影响 4 题，不加新机制。

### Day 5：错题分类（✅ 已完成）

每道错题只归一个主因："改哪一处最可能让它变对"，从最便宜的修复开始判断（答案形式 → 阅读 → 停止 → 查询 → 检索器）。详见 `docs/BADCASES.md`。

| 错在哪（Agent，129 道错题） | 题数 | 含义 |
|---|---|---|
| 阅读侧：答案形式 35 + 证据够了仍读错 39 | 74（57%） | 证据拿到了没读对；答案形式那部分只是写法问题，最便宜 |
| 搜索行为：过早停止 29 + 白搜 7 + 查询差 3 | 39（30%） | Agent 特有，V2 策略要解决的 |
| 检索器能力：缺第二跳 / 缺实体 / 未命中 | 12（9%） | Static RAG 有 83 题，多轮基本解决了 |

结论：**多轮搜索把"搜不到"基本解决了，但错误转移到了"读不对"和"停太早"**，所以净提升只有 7 题。另外检索有干扰：10 道 Direct 会的题，给了检索结果反而答错。

### Day 6：回归与波动（✅ 已完成）

| 步骤 | 做了什么 | 结论 |
|---|---|---|
| 6.1 答案规范 | 提示词要求是非题只答 yes/no、照抄文档里的答案原文 | 单轮 Direct +6 个点、显著；**Agent −6 个点**，已回退。金标写法本身不一致；而且对多轮 Agent 没有局部改动，77% 的题搜索路径变了 |
| 6.2 解码波动 | Static RAG 和 Agent 各用温度采样跑 3 个 seed | **证据召回优势在所有设定下都显著（+8.5～+12.5）**；EM 差距 −2.0～+4.5、符号会翻。Agent 28% 的题换 seed 结果就变（Static RAG 6%） |

V1 的结论因此定为：**多轮搜索稳定地提高了证据召回，但准确率没有稳定优势，瓶颈在下游（阅读、停止）**。从 V2 起方法比较都报贪心 + 3 个 seed。

### Day 8：多路召回（检索部分 ✅，2026-10-02）

检索服务从一路变三路：BM25、Dense（e5-base-v2 向量检索，FAISS 精确检索）、Hybrid（两路各取 20 条，RRF 按名次融合），走同一个 `/search`，用 `method` 区分，默认 BM25（V1 原样可复现）。
发现（validation，原问题搜一次）：Dense 召回@3 0.71 vs BM25 0.57，比 V1 的 BM25 多轮 Agent（0.68）还高；等权 Hybrid 没有超过 Dense，比较题上更差。BM25 匹配"提到"，Dense 匹配"关于"；两路互补的部分不多（只有 BM25 找到的金标 20 段，只有 Dense 找到的 79 段）。检索耗时 8～65ms，远小于一次模型调用（约 500ms）。
在全局里的意义：V2 的"自适应选检索器"在这个数据集上空间可能不大，Dense 本身就是一个便宜的强基线；Day 9 的强基线要同时试 Dense + 重排和 Hybrid + 重排。

**Dense 版本基线（2026-10-02）**：Static RAG 证据召回 0.565 → 0.710，Agent 0.677 → 0.735，但准确率没动（Static RAG −2.0、Agent +2.0，都不显著）。证据全齐的题多了，多出来的那部分大多"补上证据还是答错" → **瓶颈已经从检索转到阅读和停止**。这一步确认了 V2 的重点：自适应策略不解决"搜不到"，解决"怎么读、怎么停、要不要重排"。

**路由上限分析（加了第二个数据集 2Wiki）**：每题事后挑最好的一路（完美路由器），也只比最强的固定一路多 3～5 个点（HotpotQA +5.5，2Wiki +3.4），57%～70% 的题两路打平。最强的那一路依数据集而变（HotpotQA 是 Dense，2Wiki 是 Hybrid）。
而查询构造的影响大得多：2Wiki 上把整句问题换成"实体 + 关系"的子查询，召回从 0.59 升到 0.97。
→ **V2 主线调整**：选检索器降为小消融；重点放在查询改写 / 问题拆解（Day 10）和"要不要重排、何时停"的成本权衡上；2Wiki 作为第二个分析集，专门测拆解和跨数据集稳健性。

### Day 9：精排 + 强基线（✅ 2026-10-02）

加了 Cross-Encoder 重排（bge-reranker-base，20 条候选、GPU 约 16～22ms）。检索服务的 `/search` 多一个 `rerank` 开关，和选检索器互相独立。
- 重排让前 3 条召回涨 11～17 个点，并且**抹平了检索器之间的差距**（重排后 Dense ≈ Hybrid）。
- HotpotQA 的 **B3 强基线 = Static RAG + Dense + 重排（只搜一次）**：EM 0.405，比 V1 的 Static RAG 高 8～9 个点，4 个解码设定都显著。
- **关键发现**：在这个强检索下，多轮 Agent 不比单次强（4 个设定都不显著），成本 4～5 倍。
- 在全局里的意义：**V2 主线改成"按需升级"（级联）**——默认走便宜的 B3，只在不确定时升级成多轮。两者逐题取较好的上限比 B3 高 8～13 个点。

### Day 10：查询改写（✅ 2026-10-02）

三组公平对照，都用固定检索计划（每题搜几次是定好的，只比查询写得好不好），检索栈和作答提示词与 B3 相同：
- 只看问题的一次性改写**代替**原问题：显著更差（EM −8.5、召回 −10.8）
- 两跳、第二跳不看证据：白搜（EM −4.5 显著更差）
- 两跳、第二跳看第一跳结果：召回 +4.5 显著、EM +2.0 不显著；两段全齐 0.685 → 0.770
- 意外收获：改写那一步"拒绝再搜"的题（56%）证据和 B3 逐条相同、准确率完全一致 → 这是按需升级的现成判据
- 在全局里的意义：查询改写的价值不在"改写一次"，而在"根据已看到的证据改写"；升级信号也落到了实处

### Day 10.4：2Wiki 上的拆解与改写（✅ 2026-10-02）

2Wiki validation 800 题（4 类题型各 200），B3 同样是 Dense + 重排、只搜一次：

- 看第一跳结果的证据改写：EM +4.0 显著，组合题 0.105 → 0.245、桥接实体召回 0.077 → 0.474
- "拒绝再搜"在 2Wiki 上 385 题零翻转 → 两个数据集都成立
- 在全局里的意义：多跳拆解必须"搜一步、看一步"；按需升级的判据在两个数据集上都可靠，可以进 Day 11

### Day 11：按需升级（级联）（✅ 2026-10-03）

流程：B3 先搜一次（Dense + 重排）→ **门控**决定要不要花一次模型调用去**探测** → 探测时模型写了新查询才搜第二次，否则用第一跳证据作答（`agent/cascade.py`）。
- 门控信号：重排第 1、2 名的分差（零成本，分差大 = 另一段证据多半没搜到）；门槛跨数据集选
- 贪心下可以用已有运行**离线精确推算**任意门槛，在线复核逐字一致
- 3 个采样 seed、和同 seed 的 B3 配对：

  | − B3 | HotpotQA | 2Wiki | 成本 |
  |---|---|---|---|
  | 分差门控（探测约 3 成的题） | +1.0～+1.5，0/3 显著 | +2.6～+3.9，3/3 显著 | 约 1.4 倍 |
  | 每题都 agent 探测 | +2.5～+6.0，2/3 显著 | +2.0～+6.2，2/3 显著 | 约 2 倍 |
  | （对照）全量多轮 Agent | 不如 B3 | — | 约 4 倍 |

- 收益拆分：能跨数据集迁移的是"缺证据时再搜一次"（两边 +2.3～+2.5）；"模型有把握时直接作答"在 HotpotQA 上 +5.5、2Wiki 上只剩 +2.1。只换作答格式没用（2Wiki 上反而显著变差），B3 不改
- 在全局里的意义：V2 的核心动作"升级 / 不升级"已经落地，得到一条质量–成本曲线；Day 12 主实验在这条曲线上和 B3、全量 Agent 比

## 8. 面试一分钟版（随进度更新）

> 我做的是一个自适应的 Agentic Search。出发点是 Search-R1 这类方法只奖励答对，不考虑检索成本，简单题也会多搜。我的思路类似搜广推里的算力分配：让 Agent 根据问题和已有证据，动态决定走哪路检索、要不要重排、什么时候停。
>
> 工程上我先搭了一个可复现的评测框架：所有方法共用同一套预算定义、动作解析器和评测器，保证比较公平；检索工具的接口拿不到题目编号，只有评测器能读标准答案，从结构上防止泄漏；每次实验都记录代码版本、配置和完整轨迹，可以逐题重放、做错题归因。
>
> 我在 HotpotQA 上先做了检索体检：只拿原问题搜一次，前 3 条能找齐两段证据的只有 28%，因为第二跳的实体根本不在问题里；而比较题一次就能找到大部分证据。这说明多轮搜索是必要的，而且不同题需要的搜索量不一样，这是自适应分配的依据。
>
> 在 200 道验证题上，拿原问题搜一次就把准确率从 12% 提到 32%；让 Agent 自己多轮搜只再多 3 个点，而且不显著，成本却是 4 倍。我拆了原因：Agent 自己改写的第一个查询往往比原问题更差，多轮的收益全靠多搜。另外用金标段落做了一个理想证据上限，只有 54%，说明阅读和答案格式的损失比检索还大。所以固定地多搜不划算，要按题目决定花多少算力、花在哪里。
>
> 为了确认结论不是随机波动，我又用 3 个采样 seed 重跑：证据召回的优势每次都显著，准确率的差距却会翻符号。所以 V1 能下的结论是"多轮稳定地提高了召回"，而不是"提高了准确率"。
>
> 我还给每道错题归了一个主因：多轮搜索把"搜不到"的错误从 83 题压到 12 题，但错误转移到了"读不对"（74 题）和"停太早"（29 题），所以净提升很小。这说明下一步的重点不是搜更多，而是搜得准、停得准、读得对。
>
> 看轨迹时还发现，大约一成的搜索一篇新文档都拿不到，还有不少题在证据已经齐了之后继续搜，或者把搜索次数都花在一个实体上。所以"这次搜索还能带来多少新信息"和"还剩多少预算"是决定要不要继续搜的关键信号。
>
> V2 第一步我加了向量检索和混合检索。一个反直觉的发现是：向量检索只搜一次，召回就超过了 BM25 Agent 搜多轮；而 BM25 和向量做等权融合反而不如单独用向量。原因是两者擅长的不一样，BM25 匹配"提到"，向量匹配"关于"，而在这个数据集上后者更重要。所以强基线不能想当然地定成"混合检索"，要用数据挑。
>
> 接着加了重排。重排一次只要十几毫秒，单次检索的准确率就从 30% 涨到 40.5%，4 个解码设定都显著，还把检索器之间的差距抹平了。更关键的是，在这个强检索下，多轮 Agent 已经不比只搜一次强了，成本却是 4 到 5 倍。所以我把 V2 的问题改成了"什么时候值得从单次升级成多轮"，也就是推荐里的级联：大部分题走便宜的强基线，只把不确定的题升级。两者逐题取较好的上限比强基线高 8 到 13 个点，这就是要去拿的空间。
>
> 具体做法是先搜一次加重排，用重排第 1、2 名的分差判断证据缺不缺，只给三成左右的题追加一次"要不要再搜"的探测。门槛是在另一个数据集上选的，3 个采样 seed 复查下，2Wiki 上每次都显著提升约 3 个点，成本只多 40%；HotpotQA 上也都是正的，但不显著。拆开看，原因是分差只抓"证据不够"，而 HotpotQA 的损失更多在"证据够了但读错"。如果每题都让模型看一眼第一跳再决定答还是搜，两个数据集上都多数 seed 显著，平均高约 5 个点，成本约 2 倍。两种方案都比全程多轮 Agent 又好又便宜。
>
> （Day 14 后补：主实验的质量–成本曲线。）
